# Claude 如何缩小 OpenSSH 攻击面：先检查准入，再解析不可信输入

**一句话结论：** 让 Claude 找安全问题，不一定要让它找出一个可利用的 CVE。另一条路线是先确认「未经认证的请求究竟能够跑进哪些代码」，再把原本不该暴露的解析器、认证分支和配置组合移到准入检查之后。适合维护网络服务、协议解析器、网关及有大量配置开关的老项目；前提是能够建立可复验的执行轨迹和行为回归。

本文精读 Chris Rohlf 于 **2026 年 10 月 20 日**发表的 [Using Claude to reduce the attack surface of code](https://www.anthropic.com/research/attack-surface-reduction)。并对照 [OpenSSH 10.6 上游发布说明](https://www.openssh.com/releasenotes.html)确认其中一项修复确实进入正式版本。文章发表于本期之前 11 天，不把它包装成今天的新发布。

## 不找到漏洞，也可以让一批未知漏洞更难触及

传统 AI 安全审查喜欢回答：「这段代码有没有越界写、注入或鉴权绕过？」但逐个找 Bug 还有另一个问题：修好了已知漏洞，也不知道多少未知漏洞仍暴露在攻击者面前。

Anthropic 的研究换了一个问题：对于某种部署配置和协议阶段，**哪些代码根本不应该由不可信请求触发？**

例如，服务管理员禁止了一种算法，服务却仍先反序列化该算法的密钥，再判断该算法是否允许。这不等于反序列化器存在已知漏洞；但如果解析器今后被发现有漏洞，原本不启用该算法的部署也可能受到影响。减少可达路径，就能缩小未知缺陷的暴露范围。

研究方使用 Claude 分析 **25 个开源项目、合计超过 500 万行代码**，涉及 C、C++、Java、PHP、Python，盘点超过 **17,000 个配置项**，其中 **3,842 个**被判断与安全相关，报告 **493 项攻击面或配置问题**。这些数字来自 Anthropic 自身调查，不是第三方逐项复验，更不是「493 个可被利用的漏洞」。

项目被分成 10 个 Public、11 个 Gated 和 4 个 Private。11 个需认证的 Gated 项目均被发现有非预期的认证前可达路径；其中分别报告了 **93 项默认配置下不必要的认证前暴露、37 项过早执行或记录状态的路径，以及 61 组会削弱认证前控制的配置组合**。这些分类数字并非全体 493 项的简单分项合计。作者特别说明，这些问题本身均不能直接认定为立即可利用。

## 三轮审查，而不是把整个仓库一次性塞进上下文

团队将方法组织为三轮扫描。每一轮**以新上下文开始**，仅接收上一轮的简短交接材料。这个设计既限制上下文膨胀，也避免前一轮未经验证的猜测自动变成下一轮的事实。

### 第一轮：默认配置下，什么东西不该被访问？

先列举外部输入入口与默认配置，建立实际可达路径，再寻找「默认功能根本不会使用，却可以被请求触发」的代码。候选整改是添加更早的准入检查，而不是贸然删除整个功能。

每个发现需要动态执行轨迹确认。对于默认配置改动，原方案同时运行项目自带测试与黑盒回归，对比基线和修改版，要求默认行为一致。**如果新检查会改变非默认配置行为，交给人类判断，不自动合并。**

### 第二轮：认证、交互或状态机检查是不是来得太晚？

检查服务是否在认证前、用户交互前或协议合法状态转换前，就运行了复杂解析器、更新了持久状态、验证了昂贵签名。

关键不是给函数贴一个「危险」标签，而是沿真实调用链标注门槛与代码之间的顺序。修改建议可能只是将检查前移，或在进入深层解析前添加一个 Guard。

### 第三轮：两条合理配置，组合后有没有悄悄失效？

这是论文式工程文章里最有意思的一轮。Claude 找到 **162 组**未明确记录、也不会报错或警告的安全敏感配置交互：其中 **94 组**会静默关闭某种安全控制，另外 **68 组**导致同一控制在不同入口、顺序或作用域表现不一致。

例如，四个互不相关的项目都出现了相似情况：访问拒绝规则按主机名编写，但反向 DNS 查询被关闭。服务只有客户端 IP，却拿它和主机名模式作字符串比较，拒绝规则永远不会匹配，结果变成 **fail-open**。

另一个案例中，原本用于「延后客户端证书校验」的选项，与「必须使用客户端证书」组合时，实际把证书校验关掉。作者指出，这种组合已存在 **21 年**。这里不需要模型发明新的攻击技巧；它需要理解配置组合的语义，并通过运行确认真正发生了什么。

## OpenSSH：两次补丁才把限制放到正确位置

最具体、也最容易独立核查的案例是 OpenSSH。

**10.4：检查发生在解析之后。** Claude 追踪 sshd 的认证前路径，发现约 **4,500 行**实验性 ML-DSA-44 后量子签名相关代码，即使该算法未启用，也可以被尚未认证的客户端触发。原逻辑会先解析客户端提交的密钥；遇到证书时，甚至先验证内嵌 CA 签名，然后才检查算法是否位于允许列表。Anthropic 估计这批代码约占默认 sshd 认证前可达代码的 **16%**。

**10.5：外层算法名称检查仍有两个缺口。** OpenSSH 将检查提前，但客户端声称的算法名与实际密钥 Blob 内嵌的类型字符串可以不同：外层声称 ssh-ed25519 通过检查，内部却指向其他解析器。证书场景中，CA 公钥反序列化和签名验证同样可能先于 CA 算法准入检查执行。

**10.6：在解析层确认真正要处理的类型。** 最终改动将准入检查放进密钥解析流程：读取必要的类型元数据后，先依据 PubkeyAcceptedAlgorithms 等允许列表判断**实际编码的密钥类型和 CA 签名算法**，再进入相应的复杂反序列化或验签步骤。

下列伪代码只是这一设计的结构化说明，**不是 OpenSSH 源码或补丁**：

~~~text
encoded_type = read_minimal_type_metadata(request)
if not policy.permits(encoded_type):
    reject

if request.is_certificate:
    ca_type = read_minimal_ca_signature_type(request)
    if not policy.permits_ca_signature(ca_type):
        reject

key = deserialize_supported_key(request)
verify_as_required(key)
~~~

这次迭代的工程教训十分具体：**不能只校验请求自报的类型；检查应绑定真正决定后续解析路径的内部类型。**

### 一个不能忽略的版本细节

OpenSSH [10.6 发布说明](https://www.openssh.com/releasenotes.html)在 Bugfix 中明确列出：解析密钥和 CA 签名时应尽早依照允许列表检查，并注明这项修改由 Chris Rohlf 在与 Claude、Anthropic Research 协作中提出并反复反馈。这是来自项目维护者的独立确认。

但同一份 10.6 发布说明还在 New features 中写明：**启用了混合后量子签名算法 ssh-mldsa44-ed25519**。10.5 的实验算法此前并未默认启用。于是，「10.6 的默认配置永远不会进入 ML-DSA 解析器」就是错误结论——在允许使用该算法的配置下，解析器仍然需要工作。

Anthropic 所说「约五分之一的代码不再可由认证前请求触及」，是其研究测量口径，**不能忽略版本间默认算法集合发生变化，就直接当作 10.4 与 10.6 默认部署的同条件 A/B 数据**。上游确认的是尽早执行准入检查的修复，不是独立复核了 4,500 行、16% 或 20% 这几个统计数字。

## 为什么这种方法适合 Agent，为什么仍需人审

LLM 擅长跨文件联系配置、调用链和状态机，提出「这里的检查是否太晚」这样的调查假设；工具则把假设落成源码定位、动态轨迹、测试和差分。相比让模型直接声明「这里安全」，它更接近一条可检查的工程流水线。

但模型有几个无法靠更长提示词消除的限制。

**静态推断可能漏路径。** 反射、条件编译、动态模块加载及平台差异都可能改变可达性。动态追踪只覆盖实际运行到的分支，也不能证明不存在其他路径。

**回归通过不等于行为完全等价。** 原研究要求默认配置下测试及黑盒结果一致，这是最低限度的行为保护，不是形式化等价证明。应额外覆盖特定配置组合、认证状态转换、拒绝路径和负例。

**配置组合可能是业务意图。** 某个看似冗余的非默认入口可能是故障恢复机制。修改禁用规则可能切断合法用户；这就是原研究把非默认行为变化交给人工决策的原因。

**Agent 的权限不应随着调查需求自动扩大。** 安全扫描阶段默认只读，构建和动态测试放在隔离环境中；生产配置、发布及对外披露仍需原项目授权。动态测试只针对自有或明确获授权的实例，不向公网系统做未经许可的探测。

## 证据与社区：哪些成立，哪些还欠一份数据

证据强度分为三层。**第一层是 Anthropic 的 25 项目调查**：有技术过程和汇总数字，但大多数项目匿名，缺少完整数据集、模型版本、逐项追踪和假阳性统计，无法独立重算 493。

**第二层是 OpenSSH 的上游确认**：正式发布记录清楚描述了检查位置的变化，并明确署名协作来源。独立证据直接支持「具体修复已被接受」，不能自动外推到其他 24 个项目。

**第三层是外部安全报道和讨论**：[The Next Web 2026-10-21 的报道](https://thenextweb.com/news/claude-attack-surface-reduction-493-issues-openssh)和 [al-ice.ai 2026-10-24 的技术分析](https://al-ice.ai/posts/2026/10/anthropic-attack-surface-reduction-openssh-mldsa-october-2026/)讨论了这项方法，也提醒多数问题并不是可直接利用的漏洞。但它们主要依赖 Anthropic 原文，**不是独立重新跑过 25 个项目的实验**。

OpenSSH 维护者在同一版本说明中强调，收到的 AI 安全报告相当多，许多报告经威胁模型审视后不具安全影响；欢迎提交者附带人工分析、测试和补丁。这比「让模型疯狂扫仓库然后提 Issues」更能反映真实开源维护流程。

## 最小可复用清单

- [ ] 为每种服务角色整理网络输入入口、认证门槛、协议状态和有效配置。
- [ ] 分别审查默认配置可达性、门槛前执行路径、配置交互；每轮独立记录和交接。
- [ ] 区分请求**自报类型**和实际编码类型，验证它们是否能选择不同解析路径。
- [ ] 为每条候选发现附源码位置、预期门槛、动态轨迹、触发配置和影响范围。
- [ ] 修改前保存构建、配置及回归基线；修改后同时测试允许与拒绝路径。
- [ ] 非默认配置行为改变、权限边界改变或协议兼容性变化，一律由 Maintainer 审核。
- [ ] 分别记录发现数、维护者确认数、已合并修复数和实际暴露面变化，不混用。
- [ ] 若要报告「减少多少代码可达」，固定构建选项、默认算法集合、配置、输入语料和覆盖口径。

如果要从 OpenSSH 开始核对配置，先在**隔离测试环境**中查看本机生效值，例如执行 sshd -T 并检查 PubkeyAcceptedAlgorithms；这只能证明配置结果，不能取代源码控制流或动态覆盖实验。

## 不适用场景和结论

没有可信基线、不能运行服务、生产功能的非默认组合高度依赖兼容性，或者没有 Maintainer 可以判断行为变化时，不要让 Agent 自动修改安全门槛。对于必须接受任意未认证输入的公开解析服务，也不能简单把全部输入处理都移动到认证后；应先建立真实威胁模型。

**这篇实践最值得学的不是「Claude 找到了 493 个问题」，而是把安全审查目标从「找出具体漏洞」改成了「证明不必要的代码不会被不可信请求执行」。** 让 Agent 帮忙发现路径、提出门槛和设计试验；让运行轨迹、回归结果及维护者作最终裁决。OpenSSH 的 10.5 到 10.6 迭代同时提醒我们：一个看似正确的外层检查，可能仍然挡不住内层解析路径。

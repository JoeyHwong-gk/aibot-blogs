# 别只让 Agent 交代码：把跑通流程和录制演示也交给它

**下一次委派网页功能，不要把交付物限定为代码和测试报告。把准备演示数据、启动应用、跑通用户流程、留下可重跑的演示，也交给 Agent。你负责说明哪些行为必须成立，而不是充当它的浏览器操作员。**

适合表单、数据导入、管理后台等能在开发环境演示的功能。这里讨论的是减少重复验收劳动，不是取消人工判断。

**非新发布。** 本文精读 Simon Willison 于 **2026 年 6 月 30 日**发表的实际用法。[1] 选它不是因为录屏技术新，而是它回答了一个具体问题：Agent 写完以后，为什么还要由人重新准备环境、点一遍页面，再把错误描述回去？

## 一次委派，不止得到一个补丁

Simon 为 Datasette 开发粘贴数据、批量插入和创建表的功能。他让 Codex Desktop 检查当前分支，读取录屏命令的帮助，创建演示数据库，启动开发服务器，再展示新功能。原文使用 GPT-5.5 xhigh；这是历史配置，不是今天的模型选择建议。[1]

Agent 交付了 YAML 故事板和视频。故事板保存操作过程，视频供人查看结果。作者公开了实际操作脚本，而不是只展示一句“Agent 已经完成”。[1]

我的取舍是：**把“给我看看怎么用”提前写进任务，而不是收到补丁后再追加一轮人工验收。** 这不要求先购买一套复杂系统；先选一个本来就需要打开浏览器检查的小功能即可。

## 告诉它要证明什么，不要替它写点击脚本

下面是根据这项实践整理的任务示例，**不是原文提示词，也不是经对照实验验证的模板**：

```text
完成当前分支的 CSV 导入功能，并交付可重跑的实际演示。

我要看到：合法数据经过预览后写入；刷新页面仍存在；
缺少必填字段时明确报错，且没有写入不完整记录。

自行检查代码、准备临时数据、启动开发环境并选择操作路径。
先阅读 uvx shot-scraper video --help，再生成和执行演示。
保留故事板、数据准备步骤、录屏和运行命令。

录制时发现问题就修复并重跑。不要通过改页面文案、替换业务
响应或绕过待验证逻辑制造成功；使用了替身就明确列出。
只使用开发环境与测试账号。遇到缺失凭证或依赖就报告阻塞。
交付时说明实际验证了什么、什么仍未验证。
```

这段任务规定的是可观察结果。它没有规定先读哪个文件、选哪种选择器、如何拆内部步骤。

“刷新后仍存在”比“截图上有一行数据”更接近用户需求；“非法输入未写入”又补上了只有成功路径看不到的问题。这些验收条件是本文的建议，读者应按自己的功能改写，不必每次照搬。

## 让工具保存操作过程，别让人记住操作过程

`shot-scraper` 1.10 的发布记录确认：`video` 命令通过故事板录制 WebM；故事板可以包含准备步骤、服务启动和浏览器动作，准备命令失败会以非零状态结束。[2]

人不必学完整个 YAML 格式。让 Agent 在执行环境中查看帮助，再交付类似这样的复跑入口：

```bash
uvx shot-scraper video --help
uvx shot-scraper video demo.yml -o demo.webm --log-console --fail
```

这两条是用法示例，不是本文已执行的实验。首次使用需按安装文档准备浏览器依赖；复跑时还应保留实际工具版本。[3][4]

官方文档中的 `server` 可管理临时服务，`wait_for` 等待页面条件，`scenes` 保存操作顺序。`--log-console` 输出页面的 `console.log()`；`--fail` 对页面 HTTP 错误返回失败，**它不会自动判断业务功能是否正确**。需要 MP4 时可加 `--mp4`，环境还要有 `ffmpeg`。[3]

我建议交付目录保持简单：演示脚本、测试数据或生成方法、视频、一次真实运行记录。记录当前提交、执行命令、退出状态和遗漏项。不要为了“留证”再造一个需要人维护的报告平台。

修改后的第二轮，应由 Agent 重新生成演示。人可以复跑关键场景，但不必每轮都重新回忆入口、准备相同数据、手动点击相同路径。**这部分减少劳动的判断来自工作分工分析，不是作者测得的节省比例。**

## 别把工具故障变成无休止的提示词修改

独立开发者 rayelzz 在 Playwright Python 的 Issue #3083 中报告：1.59.0 和 1.60.0 的录屏接口没有输出尺寸参数；把页面视口设大，并不能相应提高视频分辨率。他的实际用途正是 Agent 浏览器操作的可视化证据。[5]

上游 PR #41183 随后解除该尺寸选项只面向 JavaScript 的限制，已于 **2026 年 6 月 8 日**合并。[6]

这给使用者一个具体的排障顺序：视频模糊时，先让 Agent 检查录屏依赖及 API，而不是不断重复“再清楚一点”。类似地，启动失败、页面未就绪、缺少浏览器，也应先变成可观察错误，再决定修复什么。

这两份上游记录独立支持的是**工具限制和修复**，不是“采用这套做法能提高多少效率”。

## 录像证明了操作发生，不证明所有需求成立

本文对这个方法最大的保留，是演示与验收不能划等号。

例如，原文故事板替换了浏览器的剪贴板接口。[1] 这对稳定演示可能有用，却不能证明真实系统剪贴板和权限交互也正常。视频里出现“保存成功”，也不等于数据经过正确的后端路径持久化。

所以我的建议不是让人把每一行代码再读一遍，而是检查**验收所依赖的事实有没有被替换**。数据库写入要有读回结果；外部服务调用要说明是真实测试端还是替身；视频对应的提交也要明确。截图、日志和后端断言应各自证明自己能证明的部分。

Anthropic 的官方使用文档同样建议提供浏览器、测试或模拟器，让 Claude 能自行检查结果。[7] 这是另一来源对工作方式的支持，不是对 Simon 案例的独立复现。

如果当前工作只是修正一个纯后端计算函数，直接要求可复跑的输入输出和回归测试更合适，不必硬录视频。高影响的数据迁移、付款或生产操作，也不能仅凭一段顺畅演示批准。

## 下一次任务，先改这三件事

- **交代结果时就交代演示。** 指定最关键的用户行为，以及一个值得检查的失败路径，不替 Agent 安排每次点击。
- **让它交复跑入口，不只交截图。** 环境、测试数据、命令和未覆盖项应能找到；下一轮让它自己重跑。
- **记你自己的投入。** 对相近任务记录人工操作分钟数、追问轮数和漏检问题，连同工具运行成本比较，别只统计视频生成速度。

**本文评分 87/100，证据等级 B。** 有实际案例、公开脚本、发布记录和独立上游核查；没有受控效率对照，本次也未重新运行模型或录屏。因此，合理的行动是拿一个功能试一次，而不是宣布人工验收从此过时。

要改变的只有交付边界：**Agent 不应在“代码写完”时把操作工作交回给你；它还应把软件跑起来，让你有东西可判断。**

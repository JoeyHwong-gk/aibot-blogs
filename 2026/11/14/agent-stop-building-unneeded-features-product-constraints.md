# Agent 把 API 写好了，我却把它删除：委派编码前先说清什么不该做

**一句话结论：** 当编码 Agent 已经能快速交付一个“功能正确”的系统，人最该提前写清的未必是实现步骤，而是**产品目的、不能破坏的旧行为，以及明确不做的功能**。否则，它可能用很短时间把一个根本不需要的功能做得非常完整。适用于网站迁移、已有产品重构、需求模糊的功能开发；不适合把“删掉功能”当成所有项目的默认答案。

这篇不是 2026 年 11 月的新文。Alex Cloudstar 的原站标注 **10 月 24 日**，DEV Community 版本标注 **10 月 23 日**。选它，是因为案例里有一个常被高效率叙事掩盖的返工：Agent 成功完成了 API 的设计、实现和测试，随后人决定把它整个删除。

## 一、32,784 行不是成绩单，删除才是故事的开头

作者在 2026 年 10 月 21 日晚至 23 日早间，用 Claude Code 将个人网站从 Astro 迁移到 **Next.js 16（Cache Components）**，重做页面和路由，并依据搜索关键词数据调整 **228 篇文章**的标题、描述、标题层级和开头。原文报告大约 **100 次 Git 提交、11 个合并 PR、543 项测试通过、旧网址最终零失效**。产生的 **32,784 行代码变化**包含 MDX 内容、测试、fixture，甚至后来删除的实现，不能当作生产力倍率。

传统做法往往先明确产品是否需要某个 API，才预算设计和实现成本。Agent 让顺序倒了过来：实现过于便宜，开发者容易先让它“顺便做好”，之后才认真问一句——**这个东西该存在吗？**

作者原本让 Claude Code 构建了供外部使用的 JSON API：文章、项目数据、OpenAPI 描述，还给旧路径增加弃用响应头，把新接口整理到 `/api/v1`。技术上已经相当完整，而且有测试。

随后，他删除了整个 API。理由不是“代码质量差”，而是**这个站点是用于展示个人作品和获取搜索流量的作品集**，并没有实际使用者需要这组数据接口。站点已经提供 `llms.txt` 以及 Markdown 内容协商入口。作者报告，移除 API 后静态页面数从 **1,093 降至 596**，少了 **497 页**。

注意因果：497 是减少的静态页面数量，**不是节省的人工小时数**。作者主观认为如果更早定义网站用途，可避免约一天的无效建设；但他没有公布时间追踪、模型费用或新旧流程对照。最可靠的结论是：一个已完成、已测试的特性仍可能没有产品价值。

## 二、Agent 真正弄错的，不只是新增功能

迁移有条很硬的旧系统约束：**旧站点能提供内容的 URL，新站点必须继续返回 HTTP 200 和真实页面**。博客分页和若干不在导航栏展示的项目页面，也属于被搜索引擎索引的资产。

Claude Code 按新设计的结构整理路由时，重定向了分页页面，把部分隐藏项目变成 404。对一个只看新版导航的人，这些路由似乎已经“不需要”；对依赖历史搜索入口的网站，它们却不能丢。

作者发现后恢复路由，将 **“Keep every URL main serves”** 写入提交和持续阅读的约束，并在后续路由改动后比较新旧 sitemap。他复盘时承认，**应该在第一天就建立旧 URL 保留测试**，而不是发现事故之后再加。

这两种返工实际上指向同一个缺口：

- **旧行为不可丢**没有成为可执行的迁移契约，所以 Agent 为了结构简洁清掉了仍有价值的页面。
- **新增能力要有需求**没有成为任务边界，所以 Agent 为了功能完整补出了没人需要的 API。

二者不能靠“写得更详细”笼统解决。前者要交给可自动失败的回归检查，后者要在实现前由人做产品判断。测试可以证明接口工作正常，**不能证明接口值得存在**。

## 三、他实际怎样安排 Claude Code

作者的做法不是什么复杂的多 Agent 框架，而是将自己的工作从“码代码”转向四种动作。

**先把负面约束放进会话起始说明。** 除保留全部旧 URL，他明确要求首页标题的换行方式、页面标题稳定性、元数据禁用词和格式规则。这里的关键不是某个文件名：原文只说放在 Agent 每次会读取的 instructions 和 notes 中，没有透露可复刻的完整 `CLAUDE.md`。隐含在开发者头脑里的要求，不会自动进入模型的有效上下文。

**把错误变成下一次会失败的测试。** 元数据约束由测试检查，结构化数据由 JSON-LD 测试检查，页面消失由 sitemap 检查。他处理缺陷时不是只改好当前页面，还加一条能抓住同类错误的验证。长期任务不需要 Agent 永远记住每句对话，它需要在新的会话中仍能读到可执行的契约。

**按人能看懂的规模合并。** 页面改版、内容审核、路由修复、审查反馈各自分批，合计约 11 个 PR。Agent 对页面内容和元数据做多轮 audit，**人筛选哪些发现值得改**，而不是让模型自动修复整张问题清单。并行只交给改动文件和依赖足够独立的任务，避免把并发收益换成集中审查和合并成本。

**读最终页面，而不是只看测试通过。** 文章标题是否像本人在说话、某个关键词是否违背个人风格、站点是否还传达正确职业定位，不能用单元测试决定。作者通过 DataForSEO 查询了搜索量、难度和排名结果，报告 **313 次 API 调用共 4.37 美元**，然后仍自己否决了一个有搜索机会但措辞不喜欢的关键词。这个费用只覆盖数据查询，不是 Agent 的总成本。

## 四、为什么这比再加一条“Agent 要聪明”有效

LLM 会根据当前目标、代码结构、最近反馈与工具可观察结果寻找合理的下一步。任务若写成“迁移并整理站点”，删掉看似冗余的路由、顺手设计规范的 API，都是局部自洽的选择。模型看不到搜索引擎已经收录了什么，也不会天然知道作者更重视职业展示而非公共数据服务。

这是**目标没有进入上下文**，不是模型缺少编码能力。额外的代码 review 只能发现实现风险，自动化测试只能验证预设行为。人若没有先确定“什么不值得建设”，Agent 越快，浪费越可能提前发生。

我的工程判断是，任务输入最好明确拆成两个不同的问题：

1. **必须保持什么？** 现有入口、数据兼容、业务规则、可复跑的验收方法；最好让 Agent 在改动前建立基线检查。
2. **允许新增什么？** 每个新增能力由谁使用、解决何种问题、如何证明必要；不能说明用途的建议先记录为候选，不直接实现。

这不是作者公开过的原始提示词，而是依据这次返工改写的一段可以试用的任务表达：

> 将现有个人网站迁移到 Next.js。目标是保持已索引页面可访问、改善内容展示和搜索入口；不是建设通用内容服务。改路由前先导出旧 sitemap，建立旧 URL 返回 200 且内容非空的回归检查。每次仅提交一组可审查的变更。任何新的公开 API、持久化能力或批量新页面，都先说明用户是谁、为何现有页面或 Markdown 入口不够，得到确认后再实现。报告测试、旧路由对照结果、仍未验证的风险。

## 五、可核查的部分与不应相信的部分

**可以直接核查：** 作者现在的[网站](https://alexcloudstar.com/)能够访问；[`llms.txt`](https://alexcloudstar.com/llms.txt)列出了页面及其面向机器读取的入口，说明被他用来替代 JSON API 的至少一条读取渠道确实存在。原文描述了明确的失败模式、补救动作和反事实改进建议。

**不能独立核查：** 本次未获取完整迁移仓库、对应的 11 个 PR、旧版 sitemap 快照或 CI 日志，因此 **543 项测试、零失效 URL、1,093→596、两日完成**均按作者自报处理。独立案例库 *ShippedByAgents* 收录了这次迁移，但也明确写着这些指标 **“Not checked independently”**；另一个案例整理站 *usecases.sh* 明确提示其中的示例 Prompt 是网站自行改写，不是作者原话。二次转载不能算第二次实验。

**缺少的效率证据：** 没有总人工工时、推理费用、审核往返、删除 API 前后的可比维护成本。作者所说“两天”是首末提交的日历窗口，不代表开发者只投入两天标准工时。且作品集网站与有真实 API 消费者的产品不同：后者删除已对外承诺的接口，可能造成更大的损失。

## 六、明天试哪三个动作

- **在下一条编码任务里先写“目标”和“不做”。** 不要只列功能；补一句谁需要它，以及哪些看似自然的扩展一律先提议、不得直接实现。
- **让 Agent 在动旧系统前建立一项旧行为基线。** 网站可以是全量旧 URL 比对；其他项目则选真实消费者依赖的接口、数据格式或回归样例。最后看执行结果，不看 Agent 自己说“已兼容”。
- **每次审核额外问一次“有没有功能应该删掉”。** 重点看新增的路由、配置、兼容层和接口；判断依据是用户价值和维护负担，而不是删代码能提高多少指标。

读完这次迁移，值得改变的不是让 Claude Code 少写代码，而是**让人提前做那些 Agent 无法从源码推出来的产品决定，让测试守住已决定要保留的行为**。

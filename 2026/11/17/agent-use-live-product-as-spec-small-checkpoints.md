# 别让 Agent 维护一份会过期的规格：Shopify 用旧应用作参照，按小步验收完成迁移

**一句话结论：当任务是迁移、重构或复刻已有系统时，别先让 Agent 写一份庞大规格，再要求它照着实现。让它直接读取现有代码和运行行为，把工作切成可审阅的小步，每步拿旧系统作对照、运行测试并留下证据。** 这对“功能必须保持一致，但实现技术要换掉”的工程尤其适用。

Shopify 在 2026 年 11 月 10 日披露：约 30 名工程师、按两人小组分工，在 12 周内将超过 300 个屏幕的 Shopify 商家应用从 React Native 重建为 Swift 和 Kotlin 原生实现，编码 Agent 完成了大部分代码。值得读的不是“12 周”这个数字，而是他们**试过写规格，发现规格本身成了返工源**，随后改变了交代任务与验收的方式。[1]

## 旧做法：把真实产品翻译成文档，再让 Agent 翻译回代码

团队最初试过常见的 spec-driven 流程：先为一个屏幕写规格，交给 Agent 实现，完成后审核。它失败在一个非常具体的地方：当 Agent 推进到同一屏幕的第三个 checkpoint 时，为第一个 checkpoint 编写的规格已经不完整，甚至错误。

原因不是 Agent 不会执行指令，而是团队额外制造了一份需要持续同步的“行为副本”。真实的旧应用里有加载态、空态、导航、异常状态以及各种操作反馈；文字规格通常只覆盖工程师当时想到的部分。后来发现一个遗漏，就要同时修正规格、实现和测试。[1]

另一个慢点是反馈。传统移动端循环要求编译、启动模拟器、导航、截图、检查、修改；Shopify 说每轮通常花数分钟。Agent 生成一屏代码很快，等待一次反馈却很慢，尤其当它无法稳定操作模拟器时。

**他们放弃的是“先把整个系统描述完”的工作方式，不是放弃明确要求。**

## 新做法：旧应用就是参考答案，但每次只比一小块

Shopify 把原 React Native 应用及其源代码作为可观察的参照。工程师先指定要迁移的屏幕，Helix 阅读旧实现，提出按顺序执行的 checkpoints；人先审核这些步骤是否合理。最初通常只构建页面骨架，第二步实现一个很小的区域，后面的步骤在前面的结果通过后才逐渐扩大。[1][2]

这对使用 Agent 的人有三个直接变化。

**第一，目标从“写一个类似的页面”变成“在相同状态下表现与旧页面一致”。** Agent 不必凭空猜测某种空态应当怎样显示，可以观察原屏幕、读取代码，并根据交互状态提取测试。旧系统是事实基线，而不是一句“保持兼容”。

**第二，任务粒度按人能否迅速确认来定，而不是按 Agent 一口气能写多少代码来定。** Shopify 的一个 PR 通常对应一个小 checkpoint；涉及 iOS 和 Android 同一功能的改动放在同一个 PR 里，便于逐项比较。先发现一处错误，就不用在几千行迁移产物里追溯它何时引入。

**第三，Agent 对结果负责到“提供可检查的证据”，而非“宣布开发完成”。** Helix 为每个 checkpoint 设置四道关：行为测试、与参考页面的视觉比较、两个隔离上下文的代码评审，以及工程师批准。失败就修复后重试，不能只因 Agent 认为已经足够好就跳过。有关测试的用例由另一个子 Agent 从旧实现生成，用于推动实现者检查非正常路径。[2]

视觉比较有个值得借鉴的细节：Helix 用 Gemini 对齐相同状态的旧、新屏幕，指出布局、间距、尺寸等差异；如果两个截图对应不同的页面状态，评审可返回 `INVALID`，要求重新采集，而不是强行判定一方有错。它也不是要求代码渲染出逐像素一致的图，而是比较可解释的界面差异。[2]

## 给 Agent 一个能操作的参照，比多写十页说明更有用

这套流程并不要求每个人都开发 Helix。它真正依赖的是 Agent 能观察并重放目标行为。

Shopify 的 Reflex 将屏幕的状态和可用动作暴露给命令行：`ls` 可以看到当前屏幕、JSON 状态和动作；`do Action [json]` 执行一个动作。实现依然使用 Swift/Kotlin，但大部分业务行为测试无需启动模拟器。团队报告两端合计 1,700 多个行为测试可在 CI 中约四分钟完成，屏幕状态操作可达毫秒级反馈；真正的 UI 仍需视觉检查。[3]

于是，一项迁移任务可以这样表达。**下面是我根据 Shopify 公开做法改写的示例，并非 Shopify 原始提示词：**

```text
目标：将旧应用的订单列表迁移到新实现，保持现有行为。
参考：旧代码路径 + 可运行的订单列表页面。
本轮范围：只实现列表空态与返回导航；暂不迁移筛选。
先读取旧实现并列出相应状态、动作、边界输入。
在旧、新实现上重放相同操作，输出状态与视觉差异。
只修复本轮范围内的差异；运行相关测试。
交付：变更 diff、失败及修复记录、通过的测试、
相同状态下的截图。发现无法判定的产品差异时询问我。
```

这个指令减少的不是“思考”，而是人充当中间翻译器的次数。Agent 可以自己观察、修改、重试；人只需针对范围和证据做决定。对于没有可运行旧系统的新产品设计，这招不能照搬，原作者也明确说那是不同的问题。[1]

## 真的节省了什么？别把产品性能当人工提效

Shopify 报告了可核查的**第一方交付事实**：30 人左右、12 周完成商家应用的原生重建；新 Android 版本启动时间 P50 从 1.71 秒降到 0.87 秒，Android 无崩溃会话比例从 99.66% 到 99.98%；iOS 启动时间 P50 从 0.70 秒降到 0.60 秒。[1]

这些数字说明新应用交付了，并显示最终产品的性能、稳定性变化；**它们不能证明“Agent 使每位工程师快了多少倍”**。团队还同步改变了架构、设备执行环境、跨平台代码组织和评审流程，没有纯人工重写的对照组，也没有公开总 token 费、失败重试次数、人工审核工时。

作者反倒承认了代价：多个 Agent 同时使用模拟器会把开发机资源吃满，PR 审核和合并队列会堵塞；旧瓶颈消失后，新瓶颈在 CI、环境、评审、协调上出现。两人小组按产品区域负责两端，每天早上审核夜间产生的 PR；他们还让 Agent 汇总当天评审意见，更新 Skills 和 `Architecture.md`，避免同一意见在后续 PR 中重复出现。[1]

这里的人机分工很清楚：Agent 负责重复实现、运行反馈、处理已知问题；人负责决定应该迁移什么、是否保留行为、能否接受差异以及最终合并。

## 独立核查：不是门禁越多，结果就越好

独立实践者 AIDive 在 2026 年 10 月 14 日把 Helix 的门禁思路改写为 Claude Code 的小规模试验，使用 tinydb、五类任务、两次重复，形成 50 次运行。其自报告结果：没有门禁时满足 35/50 项要求（70%）；加入独立生成的验收测试后达到 42/50（84%）；只加入两名评审者则是 34/50（68%）。测试门禁的单次报告成本从约 0.085 美元增加到 0.20 美元。[4]

**这是独立的、不同任务上的单人小样本试做，不是 Shopify 数据，也没有在公开资料中完成独立复跑。** 它支持一个更克制的判断：可执行的行为反馈可能比堆叠评审者更值得优先尝试。但测试也可能写错，作者记录了错误阻断与门禁互相矛盾导致停机的案例；不能把“四道门”照搬成对每个小修复都值得执行的配方。

还有一个根本限制：旧应用并不总是“正确答案”。如果旧实现本来就有 bug，机械复刻会保留 bug。因此参照应当是**当前行为的证据**，产品负责人仍须明确哪些行为要保留、哪些问题允许改变。安全、数据迁移和不可逆操作同样不能只凭屏幕对比验收。

## 明天就可以试的三个动作

1. **选一个有旧系统可参照的任务**：页面重做、API 兼容迁移或框架升级。把旧实现路径、运行入口和至少一条真实操作路径交给 Agent，而不是先要求它生成全面规格。
2. **先审三个小 checkpoint，再让它写代码**：第一个只覆盖骨架或一个行为；要求同状态前后对照、可运行测试和精简 diff。一个 checkpoint 能独立判断“通过/不通过”，才开始下一个。
3. **计算整项工作成本**：记录人的介入次数、每轮验证时间、失败重试次数、PR 审核耗时和最终缺陷。若新增测试和评审门禁的成本高于减少的返工，就删掉多余门禁。

一句话收束：**不要逼 Agent 在工作开始前把所有细节猜对。让真实系统给它反馈，让小步交付给人一个能判断的决定。** 这比单纯把 prompt 写得更长，更贴近 Shopify 在这次迁移中真正改变的工作方式。

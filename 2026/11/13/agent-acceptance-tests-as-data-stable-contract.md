# 别让编码 Agent 同时改代码和验收标准：把预期行为写成可执行测试数据

**适用场景：** 你把持续迭代的业务功能、重构或遗留系统改造交给 Codex、Claude Code 等编码 Agent，发现它每次都能把测试跑绿，但你越来越不确定测试到底保证了什么。

**一句话做法：人审核少量、清晰、以用户行为命名的输入—预期结果；Agent 负责实现功能、构建测试运行器和执行回归。把两者分成不同文件，并让“不该动的验收数据”在提交中显眼。**

## 一个看似反常的信号：测试越多，越不敢信

2026 年初，Thoughtworks 的 Matteo Vaccari 访谈了一个高度使用编码 Agent 的组织中的 26 位开发者。他问：「你信任我们的测试吗？」受访者普遍表达了相似的疑虑：最初看过 Agent 生成的测试，但新功能加入后，Agent 会一起重构生产代码与测试。几轮迭代下来，人已无法确定这些测试是否仍在检查当初同意的行为。[1]

这种返工不一定是 Agent 犯了低级错误。函数签名、模块边界变化时，测试代码需要同步调整，本来就正常。问题是：Agent 既在改变实现，也在改变判断实现是否正确的依据。人要么逐行复查膨胀的测试代码，要么因为测试全绿而直接放行。

作者指出另一种常见偏差：要求「给模块 X 补单元测试」，Agent 容易围绕当前函数调用、mock 和 stub 写断言。于是测试可能证明 A 调了 B，却没证明用户最后拿到了正确结果。更糟的是，当前实现如果本身有错，Agent 可能把错误行为也固定成「预期」。

**旧做法把“怎么实现”和“什么算对”同时交给同一个执行者。新做法不是要求人重新写全部测试代码，而是把人的注意力集中到后者。**

## 让人审测试数据，而不是审一大段测试代码

作者拿一个问候接口举例。传统 Java 测试需要组装 HTTP 请求、发送请求、读取响应、断言状态码和正文。真正需要人确认的只有几个事实：

| 场景 | 输入 name | 预期结果 |
| --- | --- | --- |
| 默认问候 | 未提供 | Hello, world! |
| 指定名字 | Joe | Hello, Joe! |
| 全空格名字 | 一个空格 | 返回输入错误 |

把它写成 YAML 或 CSV，供一个参数化测试运行器读取。作者给出的基本流程是：先设计一小段适合本业务的测试 DSL；让 AI 写解析和执行它的 runner；然后人和 Agent 都可以补案例。[1]

下面是**依据原文改写的任务表达示例**，不是作者的逐字提示词：

~~~text
为现有 /hello 接口建立可执行验收测试。
先把业务契约写进 tests/acceptance/greetings.yaml：
每个案例必须包含名称、输入，以及预期响应或预期错误。
请先展示案例给我确认，不要按当前实现自动推导预期。

然后实现读取 YAML 的测试运行器，连接真实接口运行；
测试失败时输出「案例名 / 输入 / 预期 / 实际」。
实现业务改动时可以修改生产代码；除非我明确批准新需求，
不得顺手改写既有验收案例或放宽运行器中的断言。
最后给出运行命令、失败和通过的记录，以及 git diff。
~~~

关键不是 YAML 比 Java 神奇，而是**审阅单位变了**：人一眼能看到空格名字是否被覆盖、金额为零是否允许、权限拒绝时有没有审计日志。将来 Agent 修改实现时，业务预期仍留在一份短小、可 diff 的数据里。

若输入是复杂状态，不能强行压成一张表。作者给出 Todo 应用的结构化场景：初始状态里「buy milk」已完成；用户点击取消完成；预期页面显示两项待办，且底层模型也确实恢复未完成状态。[1] 只看 UI 文本是不够的，持久状态必须一起验证。这里需要简单的 parser/printer：设置初始状态、执行动作、把结果投影成可读文本。作者提醒，如果为了测试状态而加入内部接口，必须保证它不会暴露给生产用户。

## 任务怎样分给 Agent，人工在哪儿介入？

这个分工比「请严格 TDD」更可操作：

1. **开始之前，人审业务例子。** 选代表性成功路径和少数容易漏掉的反例；错误预期不能由当前实现自己证明。
2. **把技术劳动交给 Agent。** 它写 runner、接服务层或真实接口、搭本地依赖、执行测试、修复失败；不要求人在每次小改动中指导函数结构。
3. **变更时看两份 diff。** 生产代码改动是一份；验收数据和 runner 改动是另一份。正常重构应该只动生产代码；业务规则变更才允许动对应案例；DSL 升级则需要单独审 runner。
4. **交付前做反证。** 故意改坏一个条件或算式，确认测试真的失败；检查测试失败信息是否准确；必要时再以真实服务或独立实现复测。

上述四点是对作者方法的操作化整理；不是原文声称已验证的统一 SOP。

为何值得把改动分类？原文有一张非常实用的矩阵：实现新功能时，允许改代码和验收数据，不应改 runner；重构时应只改代码；补覆盖时应改验收数据，不改代码；DSL 升级才动 runner。[1] 这能转换成 PR 检查和 CI 文件范围校验。单纯在 AGENTS.md 写「不要改测试」不是技术隔离：Agent 仍可能误改，且正常需求变化也确实需要改测试。

## 作者自己的验证，比空谈“测试全绿”更有说服力

作者描述过一个 COBOL 解释器项目：他给 Agent IBM 的官方手册，并要求本地生成的客户验收用例，在真实 IBM i 环境中得到相同结果。[1] 这比让 Agent 自己写一套测试、自己宣布通过更强——**正确答案来自外部参照物**，而不是来自刚刚生成的实现。

它也提示了 tests-as-data 的一个实用扩展：同一份测试数据，Agent 可以为新旧两种实现分别编写 runner。迁移或重写系统时，先对照旧系统/官方参考执行，再修改新系统；不要为了兼容新实现而悄悄改期望值。需要注意，原文没有附上该 COBOL 实验可直接克隆运行的完整仓库、日志或成本统计，不能据此宣称效率提升多少。

还有两种反证手段不能省：mutation testing 故意注入缺陷，检验测试能否发现；property-based testing 用大量输入探索不变量。它们分别回答「测试有没有牙齿」与「例子之外是否藏着问题」，但仍不能自动保证人的预期本身正确。[1]

## 独立核查：机制站得住，收益还没被证明

这并非作者临时发明的一套新格式。Ivett Ördög 在独立的 **Constrained Tests / Approved Scenarios** 实践中提出：用带强制断言的外部 DSL，降低 Agent 偷换或遗漏断言的可能性；Google Go 工具链的 script 测试也长期把环境、命令、预期输出和测试文件保存在可读文本中。[2][3] 这些来源支持「可执行文本测试」在工程上能实现，并不构成「编码 Agent 使用它一定更省人力」的对照实验。

另一个独立的评审来源将本文评价为具体、可操作，但认为**实证主要是定性访谈和示例，缺少新方法的量化验证**。[4] 这一批评应保留。作者引用了若干关于 AI 辅助开发缺陷增长的行业报告，却没有证明这些增长由 AI 修改测试所致；本文也不能把相关性写成因果性。

我给这篇实践 **84/100，B 级证据**。分项为：技术深度 18/20、可复用性 19/20、实证 15/20、独立核查 10/15、非重复 13/15、可核查性 9/10。B 的依据是作者一手访谈、亲历的系统开发案例以及独立可查的同类工程实践；不是因为存在严格比较实验。

边界也清楚：探索性原型、一次性脚本或已有其他强验收手段的任务，额外搭 DSL 可能不划算。解析器、runner、测试夹具仍会出错，甚至被 Agent 修改；把验收写成 YAML 并不能消除人的判断工作。真正减少的是反复阅读生成代码确认「测试到底测了什么」的负担，**但减少了多少，尚无可靠统计**。

## 明天就能试的最小版本

选一条近期反复被改的业务规则，不必迁移整个测试体系。让 Agent 把现有两个成功例、两个失败例抽成单独的 YAML/CSV，生成可运行测试，并把业务期望先交给你核对。接着给它一个重构任务，要求只改实现，最后看测试数据有没有变化。再让它注入一处已知错误，确认该测试红灯。若整个过程比直接审普通测试更费工，就暂时不要扩大范围。

**重点不是增加验收流程，而是让人拥有稳定的“什么算对”，让 Agent 自主处理“怎样做对”。**

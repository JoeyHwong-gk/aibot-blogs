# 别让 Agent 逐份修改派生文件：从已验证的设计重新生成下游产物

**一句话结论：** 当一项工作同时产出代码、配置、图纸、测试和报告时，让 Agent 维护可执行的上游设计、生成下游产物并核对一致性，比每次需求变动都让它逐份手工修改更值得尝试。人的注意力留给设计决策和真实验证，而不是充当文件同步器。

2026 年 11 月 14 日，Tim's Blog 发布了 TouchSynth 的开发记录：一台由 MCU 控制的模拟合成器，从设计、仿真到 PCB 和固件，再到实际电路测试。案例的价值不在 AI 能否替代电路工程师，而在于一项横跨多个工具、多个交付物的任务怎样避免上下游互相脱节。[1]

## 1. 人为什么不再一边生成一边改

作者根据此前端到端生成式工程经验，倾向先完成一个抽象层的规格，再让 Agent 生成下一层；他认为频繁回头零散修改前面层级，效果反而不如完整生成，并要求同步留下设计文档。这是作者的观察，而非两组实验的统计结论。

本次他在 VS Code 中使用 Claude Code / Opus 5.5，从空目录出发，给出器件采购约束和 CH32V00x MCU，最终选择带触摸键盘的模拟合成器。开发环境同时开放 Windows 上的 KiCad 和 WSL 的命令行工具。

这不是一次只写固件的任务。电路的器件值、连接关系、仿真条件、制造文件和固件控制参数，任何一处变化都可能让其他产物失去对应关系。

常见的错误委派方式是：修改原理图，再让 Agent 更新仿真，再修改固件，再补报告。每次需要重新说明前面做了什么；人最后还得判断究竟哪份文件代表当前设计。

## 2. 把需要保持一致的东西变成可生成、可核对的数据

公开仓库把器件、参数、料号和网络连接放在 `hw/design.py`，原理图及 PCB 等产物通过脚本生成。仿真有自己的网表构造逻辑，代码还专门检查它与设计源的一致性。不要把这理解成所有文件都直接由一个函数生成，更不要把一致性检查理解成全部电气性能已经正确。

仓库中可以直接检查这几个入口：[2][3][4]

| 工作 | 可执行入口 | 核对内容 |
|---|---|---|
| 电路仿真 | `sim/s*/s*.py` | 数值、曲线和输出数据 |
| 行为模型 | `sim/behav/validate.py` | Python 模型与 SPICE 的对应关系 |
| 原理图 | `hw/gen_sch2.py` | 由设计源生成 KiCad 文件 |
| 网表核对 | `hw/check_netlist.py` | 连接集合、封装、LCSC 料号 |
| 仿真核对 | `hw/check_sim.py` | S6/S7 网表的映射连接与部分器件参数 |
| PCB、制造 | `hw/gen_pcb.py`、`hw/fab.py` | 布局、布线及生产文件 |
| 实物测量 | `tools/hwtest.py` | 通过调试控制台采集测试数据 |

我核查了两个检查脚本。前者导出 KiCad 网表后比较引脚连接的集合，并检查封装和料号；尽管文件注释提及 values，所读实现没有逐个比较全部元件值。后者使用显式节点映射对比仿真和设计，电阻、电容还比较数值；它并不是对全部器件、全部仿真工况的形式证明。

这个差别很实用：**要求 Agent 交付检查器，不代表检查器覆盖了你想保护的所有属性。** 审查时直接看它到底比较了什么。

仿真报告的修订记录也显示，校准数据通过文件传递，CV 滤波网络的级间负载问题则在行为模型验证中暴露并修正。[5] 这比让 Agent 在聊天中记住一串参数再抄到另一个文件更容易追溯。

## 3. 人的介入应该发生在哪儿

根据原作者记录，布局是最需要人参与的环节。两层 PCB 自动布线没有成功，后来由人调整到四层，并指导功能模块布局和布线空间。作者报告设计至订板约 19 小时，其中大量时间耗在无需持续人工交互的布线上。制造等待约两周，不能计入所谓 19 小时完工的说法。[1][6]

这里不是说每次变化都要冻结规格。如果现实证明上游假设不可行，就修改上游并重新运行受影响的环节。应避免的是只在某个派生文件上打补丁、把冲突留给下一次会话。

从 LLM 的工作机制看，这样的分工有两个理由。第一，模型在上下文中看到的是被选取的文件和工具输出，不会自动知道其他文件已经过期。把变更集中到少数事实来源，可以降低需要同时推断的状态数量。第二，编译器、仿真器、网表比较器提供的可观察反馈，比模型重述“已经同步”更容易发现差异。它们不保证语义正确，但至少能把一类跨文件错误变成可重复的检查。

不要因此要求 Agent 重建整个工程。仅有一处简单业务代码变动时，直接修改并跑相关测试通常更经济。生成链适合本来就有重复派生关系的产物。

## 4. 最好的验证，是让生成产物面对它没有见过的现实

TouchSynth 还提前加入了音频输出到 MCU ADC 的反馈通路。完成初步人工电气检查后，Claude Code 通过 SSH 使用实验室电脑、编程器和示波器进行后续测试。仓库保留了测量数据、验证计划与真实样板的结果。[2][7]

公开的 Board 1 记录（2026-10-17）给出了这样的对照：

| 测量 | 预期/参考 | 实测 |
|---|---|---|
| 滤波器跟踪斜率 | 2.05 ± 0.2 oct/V | 2.01 oct/V |
| VCA 增益曲线 | 仿真差异不超过 ±2 dB | −0.23 至 +0.05 dB |
| 校准后 VCA 瞬态偏移 | 小于 3 mV | 0 ± 2 mV |
| 宽带噪声 | 低于 −60 dB | 约 −55 dB，未证实达标 |

其中最值得读的是脚注。相对 MCU 自己的时钟，音高误差不到 1 cent；但是示波器发现时钟慢 0.8%，绝对音高约低 14 cents。环回 ADC 的量化噪声也限制了 −60 dB 指标的验证。触摸扫描率和 MIDI 尚未测量。部分报告中的通过结论还有测量口径限制，例如增益曲线不代表绝对最大增益已测。

因此，内部自检与仿真吻合，不能替代独立参考。真实测试还揭示了固件采样和 DAC 时序的问题；手工焊接也产生了焊桥。触摸键的实际操作体验仍需人判断。

这才是可执行验证的价值：不是生成一排绿色标签，而是让实际结果有机会推翻设计中的假设。

## 5. 明天可以怎样改变委派方式

假设你正在给 Agent 一项 API 变更，涉及服务端、客户端 SDK、契约测试和文档。不必照搬硬件工具链，可以借用同一种生成与验证分工：

> 先找出当前的权威接口定义和已有生成工具，明确哪些文件是源、哪些是派生物。修改源定义后重跑相关生成步骤；不能生成的部分说明原因。交付生成命令、差异和一致性检查结果；用独立客户端验证真实服务行为。若契约必须变更，先说明兼容影响，不要为了通过检查而单独修改预期值。

这是本文提出的迁移示例，不是 TouchSynth 原始提示词。实施时可以从一个已有的 OpenAPI 生成链、协议绑定或配置生成流程入手，而不是额外建立一套管理框架。

- 先让 Agent 识别已有权威输入与派生产物，避免凭空新增第二份规格。
- 要求它复用生成命令，并留下可重复执行的一致性检查。
- 人确认上游约束和不可逆决策；发现工具能力或环境限制时，改变方案而非让 Agent 无限重试。
- 另用真实消费者或独立参考验证交付物，不把生成工具自身的输出当成独立证据。

评估收益时，记录人的总投入、执行时间、跨文件返工次数和最终缺陷，而不是只统计生成速度。实验室 SSH 应使用受控测试环境；生产设备或不可逆操作不应沿用未经确认的权限。

## 6. 证据和边界

独立硬件案例目录 Boards & Bots 于 11 月 20 日收录该项目，并指出其照片与实测曲线可查看；这是第三方核查材料，不是独立制造或复现实验。另一个外部整理也记录了触摸体验、噪声与未测项目。[6][8] 独立社区复现证据不足。

本次核对了原文、仓库说明、两份检查器源码、仿真报告和验证计划，但没有实际运行 ngspice、KiCad 或制造样板。仅一块板、没有人工基线，也没有模型费用和交互次数的完整统计，不能断言这种方法普遍节省多少时间。它展示的是如何减少跨工具、跨产物的重复人工同步，和如何识别仍然需要人介入的决策。

# 别在 Agent 提交 PR 时就接手：先确认设计，让它把 CI 跑绿再找你

**一句话结论：** 如果你每次收到 Agent 的 PR 通知后还要等 CI、复制失败日志、叫它修复，再等下一轮，那么不妨把交接点往后移：人批准设计，Agent 自己完成实现和有限次数的修复，只有达到可验收状态或真的需要人决策时才打断你。

TeraDox 工程师 A.Yoshikawa 在 11 月 24 日发表了一个生产项目复盘。项目是高尔夫学校搜索与预约门户的重建，10 月 30 日发布。他是主要设计与实现人员，另有 PdM 和外部技术顾问。[1]

## 1. 把“提交 PR”和“准备好接受审查”分开

作者披露的月度合并记录如下：

| 月份（2026） | 合并 PR 数 |
| --- | ---: |
| 7 月 | 7 |
| 8 月 | 10 |
| 9 月 | 6 |
| 10 月 | 87 |

10 月 28 日一天合并了 15 个 PR。8 月开始引入 worktree，月底转向本地设计、云端实现；高峰期并行运行 5–6 项工作。[1]

不能把这张表当成 Agent 提效实验：9 月作者忙于其他工作，10 月需求和设计更成熟，距离发布也更近，PR 粒度可能不同。它说明了一个真实项目的工作量变化，并不证明某个工具能让生产率增加十倍。

更值得关注的是等待的性质。过去，PR 出现并不意味着人可以审查：CI 可能还没结束，也可能已经失败。每一次失败都回来找人，工程师便成了工具输出的转发器。即便单次修复只需要几分钟，这种碎片化等待也会让人不敢切换到需要集中注意力的设计工作。

## 2. 交给 Agent 的不是聊天记录，而是批准后的任务合同

作者写了两个自己的 Skill：本地 `/spec` 用来反复澄清需求，云端 `/ship` 负责执行。这里的 `/ship` 是作者自定义命令，不是后来同名的官方功能。[1]

本地设计文件放在 `specs/<name>.md`。它包括需求链接、范围和非范围、变更文件与数据流、TDD 对象、预授权的决策。设计批准后推送分支，再执行作者给出的命令：

```sh
claude --cloud "/ship" --permission-mode auto
```

官方文档确认了 `--cloud` 的远端工作方式：GitHub 克隆场景下使用当前远程分支，本地未推送的提交不会自动进入云端。启动的是新会话，而非自动搬运整个本地对话。[2] 因此设计必须自包含，至少要让执行者知道哪些决定已经成立、哪些问题仍未解决。

以一个后台删除功能为例，下面是本文提供的迁移示例，并非作者原始 Skill：

```markdown
目标：管理员可以删除符合条件的草稿。
边界：已发布、有引用或不属于当前租户的记录不得删除。
验收：正向删除；跨租户拒绝；有关联记录时拒绝。
自主决策：沿用现有组件、测试与错误码。
必须询问：是否改变业务约束、迁移历史数据或修改公共接口。
```

为什么不直接让云端 Agent 看本地对话？因为 LLM 只能根据本次会话实际获得的上下文行动。聊天里已经推翻的方案、后来修改的需求，未必会在摘要中完整保留。设计文件的价值不是形式，而是让执行会话获得一组确定的当前事实。对于不可逆决策，最好让最终版本同时保留对应的测试或 ADR；任务文档可以短命，决策证据不应丢失。

## 3. 把 CI 失败留在执行会话

作者的实现流程在 PR 创建前最多做三轮审查，PR 创建后自主处理 CI，五次修复仍失败时才升级给人。遇到超出设计范围、破坏性操作，也会停止并通知。最后由人操作 Preview 环境并合并。[1]

这套做法可以用三个状态理解（本文抽象）：

| 状态 | 下一步由谁负责 |
| --- | --- |
| WORKING：实现、CI 运行或可修复失败 | Agent |
| BLOCKED：需求变更、权限问题、修复预算耗尽 | 人决策 |
| READY：当前提交的必要检查通过 | 人验收与合并 |

这里的 READY 不是 DONE。CI 只证明实际执行的断言成立，并不自动证明产品符合真实需求。也不能为了获得绿灯而删除测试、放宽断言或绕过必需检查。让 CI 的检查结果绑定到准备合并的 commit；合并前基础分支变化时，再执行必要的集成检查。

对于普通编程任务，下一次可以直接在任务指令里写：

> 自主完成实现、相关测试、PR 与 CI 修复。对可修复失败自行处理，不要每次找我；最多尝试五次，出现规格冲突或需要扩大权限立即停止。交付当前 commit 的检查结果、Preview 入口、已知限制与未验证项。不要自动合并。

五次只是借鉴此案例的预算，不是最佳常数。重复出现同一错误时，应该提前退出并带上日志、假设及已尝试动作。CI 若长时间排队，也应记录等待状态，而不是反复触发新的运行。这样可以让人的下一次注意力投入更有价值，而不是仅仅把等待藏起来。

## 4. 这套方法最容易在哪里翻车

作者报告了三个真实问题：[1]

- AI 澄清需求时仍然悄悄决定解绑交互、文案和候选范围；后来改用含图与页面流转的 HTML Artifact 辅助设计审查。
- 两个并行 PR 分别添加数据库迁移，合并后历史分叉。发布前可以重建迁移，已上线后则不能原样照搬。
- 因为实现容易，作者自己也把不必要的开户、引导流程纳入范围，导致首发变大。

这些失败都不是再增加一个编码 Agent 就能消除的。第一类属于需求决策错误，第二类属于工作之间的依赖，第三类属于人选错目标。把执行放到后台只是减少打扰，不会替代产品判断。

社区也有相似的经验：一则独立 Reddit 讨论指出，worktree 能隔离工作目录，却挡不住共享类型和配置变化导致另一项工作失效。[3] 这是对并行边界的旁证，不是对 TeraDox 项目结果的独立复现。Matt Pocock 的公开 `grilling` Skill 则展示了澄清阶段如何围绕设计决策连续提问。[4]

另一个实际约束是费用和限额：作者提到并行期间触及 Team 使用限制，另外订阅 Max。官方文档也明确云任务使用共享配额。[2] 所以不能只看后台跑了多少会话；如果人来不及验收，多启动一个任务只会多一份积压。

## 5. 明天怎么试

先选两项相互独立的小任务，不必立即建设复杂工具。把需求确认与执行拆成两个会话，让执行会话只依赖已批准的文件及可运行环境。为 CI 修复设置预算，并要求就绪通知绑定实际检查结果。人最终查看真实 Preview、关键业务逻辑及合并风险。

观察三项数据：人主动处理 CI 的次数、从首次委派到可验收的总时间、最终验收发现的缺陷和返工。只有这三项没有恶化，才值得增加并行量。若组织不允许云端上传代码，就用受控本地 worktree 实现同一交接合同，不必迁移到云端。

本文核查了原文、公开产品文档、上游 Skill 与社区讨论，未获得项目原始日志、私有 Skill、CI 明细或人工耗时；也没有独立复跑。作者的经验足以支持试行这种工作方式，不足以承诺固定的提效比例。

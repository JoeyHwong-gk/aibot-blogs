> **一句话结论：** 让 Agent 排查线上故障，不要只问“哪里坏了”，而要要求它说明**什么证据会推翻自己的判断**，再把“修复后恢复到基线”的检查留在同一个任务里。适用于性能回退、间歇性错误和多服务故障；前提是 Agent 能合法读取足够的指标、日志、追踪及变更记录。

很多人向 Codex 或 Claude Code 交代故障时，习惯把错误日志和几段代码贴进去，问一句“分析根因并修复”。Agent 找到一个看似合理的调用链，写出解释，再附上补丁。你得到的是一份连贯报告，却不一定得到正确答案。**解释得通**和**排除了其他解释**，是两件事。

OpenAI 工程师 Okay Zed 与 Cyrus Forbes 在 2026 年 11 月 19 日公开了他们处理 ChatGPT 性能回归的经历。文章涉及一套内部自动化系统，但我认为对普通开发者更有价值的不是复刻那套系统，而是他们如何改变 Agent 的调查任务：从“找一个可能原因”变为“划定影响、建立假设、主动反驳、提交证据、部署后再核验”。[1]

## 从人工带路，到 Agent 自己查证

最早，性能工程师自己查看指标和日志，对比 traces，在机器上调试，再翻代码。团队逐步积累了 **30 多个性能工具**，包括 CPU 和内存分配分析器。Codex 加入后，工程师可以直接问“为什么变慢了”，由它跨代码库、指标和 traces 搜索。但人仍要反复提示该用哪个工具、查哪个系统。这相当于工程师成了 Agent 的工具调度员。[1]

团队随后把重复的调查经验做成名为 `perf-forensics` 的 Skill：先判断何时变慢、哪些请求受到影响，再检查部署和配置变更。用历史回归案例调整 Skill 后，针对其关注的部分延迟及可用性问题，Codex 能从告警开始独立提出诊断，不再需要人逐步指挥。注意，**工具并没有因为写进 Skill 而变可靠**；收益来自 Agent 能直接访问真实数据、知道何时使用工具，以及能够检查自己的解释。[1]

他们继续把告警触发、诊断、提出 PR、等待工程师审查、部署后复核连接起来。至文章发表时，团队报告三个多月里追踪了 **1,700 多次调查**，对 **600 多个案例**进行了根因定位，平均每天启动约 **17 次自动调查**。这些数字说明任务确实在持续运行，却不能拿 600 除以 1,700 计算准确率：原文没有把两者定义成同一批可比较样本，也没有公开完整数据。[1]

## 一次非常具体的错误：服务恢复了，故障却还在

真正改变我对这篇文章评价的是一个反例。某次 ChatGPT 对话失败，初轮 Agent 顺着错误追到图片下载，认为负责定位文件的内部服务出了问题，于是把根因标记为已找到。

但独立的 Codex 审查会话发现一个矛盾：**那个文件定位服务已经恢复，图片请求仍然失败。** 如果“服务故障”是足以解释现象的主要原因，那么其恢复后为什么问题仍持续？原先的结论至少不完整。审查者没有润色诊断，而是重新打开调查，并记录尚未解释的现象。[1]

这个区别在真实排障里很常见：一条错误日志可能是真正的根因，也可能只是下游症状；一次发布与性能下降恰好同时出现，不等于发布必然造成退化。反证并不是要求 Agent 一味唱反调，而是让它针对自己的因果链回答：

- **时间能否对应？** 告警触发时间和实际开始退化的时间可能相差数小时；怀疑的部署何时真正到达受影响请求？
- **受影响与未受影响组有何区别？** 相同类型的请求是真的变慢，还是慢请求在流量中的占比增加？若某功能开关导致问题，未暴露于该开关的请求是否正常？
- **移除嫌疑因素会怎样？** 回滚或服务恢复后，指标是否回到原基线？如果没有，当前解释还缺什么？

这三类检查都出自团队公开的调查方法。它们与 Google SRE 的故障排查原则一致：假设应接受支持和反驳证据的检验，严重事故要优先减轻用户影响，再做深入根因分析。[1][2][3]

## 普通开发者怎样交代任务

不需要先搭建所谓“Agent 工厂”。如果你有一个可以运行命令、读取日志与指标的编码 Agent，下次排查服务慢、接口报错或测试偶发失败时，可以直接把任务改写为如下形式。**这是依据原文整理的可复用指令，不是 OpenAI 作者公开的原始提示词。**

```text
目标：定位本次性能/错误回归，给出可复核的原因与修复建议。
证据：可访问的监控图、日志、traces、最近部署与配置变更、相关代码。

先确认：退化何时开始、影响了哪些请求和用户、是否有未受影响的对照组。
列出最有可能的两个解释，逐条注明支持证据、反证和仍缺少的证据。
不要把时间相关性写成因果结论。若关键假设尚无法验证，请明确标为未确认。

提出补丁前，请在新的审查会话中试图推翻首选解释；如解释不成立，
继续调查，而不是为已有结论寻找修辞。

交付：问题范围、事件时间线、证据链接或命令结果、排除过的解释、
最小修复 PR 与风险。由我决定是否合入和部署。
部署后：按相同请求组、相同指标对比原基线；无改善则重新调查，
部分恢复则说明剩余问题，不要直接宣告全部完成。
```

这里的关键不是格式，而是**把判断和验证分开**。初轮调查负责探索，第二轮在尽可能独立的上下文中质疑假设。别让第二轮只复述第一轮的总结，至少给它原始指标、时间线和需要验证的主张。人在两个点介入：一是接受有代价或风险的修复方案，二是确认线上结果是否真正恢复。[1]

原文还暴露出一个容易遗漏的成本：**读 Agent 报告也是工作**。团队的初版产出了大量长篇调查文字，工程师仍得自己寻找证据。因此他们把受影响指标、时间序列、CPU flame graph 和 traces 放入便于扫描的任务摘要，并合并重复事件、按影响排序。对于单人使用 Agent 的开发者，要求结论旁边附上直接证据，比要求一份更长的“深度分析报告”更有用。[1]

## “查对”也不等于“修对”

团队人工审阅了 **100 条根因建议**，认为其中 **70% 准确**，另外 **30% 还需要完善或尚未充分建立因果关系**。这不是独立盲测，也没有披露随机抽样方式。作者还明确说，提出补丁比找原因更难：Agent 有时写出过度复杂的修复，甚至引入新问题；例如加缓存虽然可能改善延迟，却会带来陈旧数据的权衡。[1]

因此，OpenAI 让独立会话再次质疑补丁，由工程师审查 PR、决定是否合入；部署后，Agent 检查指标是否恢复。如果没有改善，就回到调查；如果只恢复部分，则记录剩余退化并另建任务。**一次代码合并不是任务完成的证据。**

这里也有读者不必模仿的部分。团队有内部云环境、服务身份、完整可观测数据、事件订阅和历史案例评测。这些能力使自动接续成为可能。一个只能看到应用源码、拿不到线上 traces 的本地 Agent，不可能凭更严厉的提示词补齐证据。遇到权限不足或观测缺口，正确输出就是“无法确认”，并说清下一步需要哪些数据，而不是继续猜测。[1]

在做历史案例回测时，他们还刻意避免 Agent 偷看到事故报告、此前调查记忆和后来才出现的指标；不然所谓“诊断准确”很可能只是答案泄漏。这也是评价自己排障 Skill 时值得保留的原则：只给它在故障发生当时真实可见的材料。[1]

## 效果有多大，证据到哪里为止

已能确认的，是作者公开了工作流、失败案例、人工审阅结果，以及三个月以上的运行量。**尚不能确认**的是：每次调查究竟省下多少工程师工时、整条故障的平均恢复时间减少多少、Agent 成本多少、补丁最终合并率多少。原文没有给出同任务的人工作业对照；我们也无法访问内部事件、审查记录和仪表盘独立复算。

独立核查方面，Google SRE 的经典排障材料支持“先划定影响，再检验和推翻假设”的方法；近期开发者社区也反复抱怨多 Agent 报告淹没人类审查者，但**未找到针对 OpenAI 这 1,700 多次调查的独立复现实验或公开 PR**。所以本文把它归类为有具体生产实践的 B 级证据，而不宣称已经证明普遍提效。[2][3][4]

对于明天就要调试的人，我会先尝试三件事：第一，把“查明原因”改成“解释并排除竞争假设”；第二，为每条结论保留可定位到具体指标、日志或命令的证据；第三，把部署后的同口径复测作为完成条件。**让 Agent 少写一点确定语气，多做一次能推翻自己的检查。**

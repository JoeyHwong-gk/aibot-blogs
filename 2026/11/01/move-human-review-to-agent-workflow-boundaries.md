# 别再逐行盯 Agent 的 PR：把人的时间留给问题定义和验收缺口

**下一次交给编码 Agent 的任务，不要默认自己要在最后读完全部 diff。** 先把需求整理成可独立交付的一条路径，让 Agent 在真实应用里跑过这条路径、留下可核对的证据，再由独立会话审查；只有证据不足或改动高风险时，才把 PR 交给人细看。

这不是“别审代码”，而是把人工注意力从默认步骤改成有理由才发生的步骤。适合已经有 CI、可运行开发环境、清晰业务负责人的小团队；并不意味着受监管系统也可以照搬自动合并。

## 人为什么成了 Agent 的最后一道串行工序

Martin Gratzer 在 2026 年 10 月 22 日的文章里写了一个很不体面的转变：以前他的时间花在审核每个 PR，现在越来越多花在**任务开始前的成形，以及发现一次失败后怎样改进整个工作环境**。[1]

他给出了自己的手写 review 评论记录：今年 1 月，Colorburst 的 25 个 PR 共留下 **126 条**；9–10 月的 **159 个 PR 是 0 条**。这只说明作者不再频繁写逐行评论，不说明这些 PR 没有缺陷，也不能直接推断审查成本下降了多少。作者也承认，自动合并刚启用几天，长期结果还不知道。

真正刺痛他的是另一个实验。他帮助土木工程师 Andreas 把 Claude Cowork 做出的地理数据原型变成项目：原型没有 Git 和 CI，几乎所有逻辑挤在一个 `index.html`，每次查询还读近 1GB 数据。给项目加上测试、静态检查、部署管线后，Andreas 开始自己指导 Agent 做业务功能，**五周开了 85 个 PR**；Martin 在 9 月批准了 48 个中的 45 个。[1]

Martin 自己不懂全部土木工程规则，逐行读上千行 PR 既费力，也不能替业务专家判断法规解释是否正确。他还承认曾让 Claude `/code-review` 找问题，自己署名转贴——修好了眼前的 PR，却没有减少下一次需要做的同类劳动。

他的转向是：**与其不断替 Agent 纠错，不如追问这类错误为何能走到人工面前。**

## 把一次委派改成三个环节

### 1. 先谈清“交付什么”，不要预先指定每个实现步骤

Martin 没让 Agent 一次吞掉整个产品。他把工作拆成 Issue，每个 Issue 是可独立上线、或者能被 feature flag 隔离的**纵向切片**。纵向意味着这项任务包含所需的前端、接口、数据和验证，而不是“先写全部后端，再补页面”。

读者可以这样交代一个真实任务（**以下是本文改写示例，不是作者原 Prompt**）：

> 让用户在订单详情页撤销尚未发货的订单。完成后我应能用测试账号从页面发起撤销，刷新后仍看到已撤销状态；已发货订单不能撤销。请先检查现有流程和相关测试，自行选择实现方式。提交前运行应用，记录成功路径、拒绝路径及实际数据库状态。涉及退款或数据迁移先停下说明。

这个任务把业务判断、应有行为和高后果边界说清楚，没有规定模型先改哪个类。Forge 的 `/forge-shape` 会先查代码与旧 Issue，再围绕尚未决定的问题逐个提问，并把结果切为可执行 Issue；它不是让人补写一大份规定动作的提示词。[2]

### 2. 要求 Agent “实际用一次”，而不只是报测试通过

作者的 Forge 工具把运行验证做进了 `ship`。核心命令见公开仓库：

```text
/forge-setup-project
/forge-ship 42
/forge-ship --guard 42
```

第一条为仓库准备可被 Agent 读取的运行说明；第二条实现 Issue #42、运行受影响功能、做新上下文审查并开 PR；第三条继续处理 CI、审查反馈和风险判定。**`--guard` 不等于默认自动合并**，自动合并需要仓库额外显式开启。[2]

这里最有用的不是命令名，而是 PR 的 `## Exercised`：记录运行了什么、观察到了什么、失败路径是什么、哪些环节**没跑到**，并附上别人可复制的复查命令。Forge 的公开执行说明要求真正触达改动路径，最好核对测试不容易覆盖的状态，例如实际存储结果；若环境没有启动办法，要写 `not exercised`，不能臆造“已验收”。[3]

这会改变你看 PR 的方式。你不再先读 30 个文件判断“看起来能用”，而是先看**用户流程是否跑通，以及证据没覆盖的地方在哪里**。一张成功截图不能证明数据库更新了；一次单元测试也不能证明真实模型接口按预期返回。

### 3. 把“是否需要人审”变成一个独立判断

`ship` 的代码审查在**新的上下文**进行，而不是让刚写完代码的那段会话自己给自己打分。`guard` 跟进 CI 与反馈；`land` 再在 PR 当前 head commit 上给风险结论。

本次核查的 Forge 源码有可读的具体标准：超过 **400 行计入范围的改动**、迁移/Schema、依赖或 CI 改动、敏感路径、削弱测试、未真实演练的运行时改动，都应进入人工审查。若机械检查通过，新上下文审查仍要指出**这些检查可能漏掉什么**，否则不能轻判低风险。[4]

低风险且仓库已选择 `Auto-merge: low-risk` 时，才会尝试合并**风险评估时的那一个提交**。新提交使结论过期。需要人工看的 PR 不应发一篇笼统总结，而应给出文件、位置和具体问题：例如“这条建筑法规是否按正确版本解释？”——这只能由 Andreas 判断，不能因为测试全绿就跳过。

## 真正有复利的部分：把漏网错误变成下一次的环境能力

文章里的两个失败案例说明了“交证据”和“证据可信”不是一回事。

一次 Colorburst 计费调整，两个新上下文审查者发现测试 fixture 使用了根本不存在的价格档位，所以测试虽然通过，却没有覆盖免费档。另一次依赖升级，针对 SVG 净化器的 **30 组特制输入**找出了 **3 条绕过路径**。作者称这些问题在合并前被修复。[1]

也有一次没被提前发现：换图像模型后，新模板大约**五周都没有标题和标签**，CI 一直是绿的，因为测试把模型响应写死了。作者后来补了调用真实模型的契约测试。这是很重要的反例：**把验证工作交给 Agent，不代表 Agent 自己选择的验证方式就足够。**

更好的复盘问题不是“下次提醒它细心一点”，而是“缺了什么信号，才让这个错误顺利过关？”可能是实时接口契约、业务数据夹具、可运行的演示路径，也可能是误报太多的 reviewer。只把确实反复出现的失效模式沉淀为工具或检查，不需要把全部偏好塞进 `AGENTS.md`。

## 独立材料支持方向，但尚未验证 Martin 的效果

可以交叉核对的，是其他团队正在解决同一种人工瓶颈。

**Imprint 的 Will Larson** 在 10 月 17 日写到：PR 的中位审核时间从两年前约 **33 分钟涨到 77 分钟**。他们让 CI 决定 `small-change` 资格，再由 Skill 快速评审；初期仅约 **10%** 的改动符合条件。他明确承认尚无充分效果数据。[5]

**Claude Code 团队** 在 10 月 15 日披露：先让 Agent 跑测试、展示输出，再由独立会话审查；低风险变更可以不需要额外人类批准，高风险仍要多人审。其团队报告 PR 合并量增长、回退比例下降，但原始数据未公开独立复验。[6]

两者支持“**按风险花人工注意力，而非一律逐行读代码**”这一工程方向；不能拿它们为 Martin 的 126→0 或自动合并可靠性做背书。

还要指出 Forge 当前源码的一处实际边界：`land` 在**没有 CI 检查、也没有配置 peer reviewer** 的仓库里，存在将相应前置条件视为通过的路径。[4] 因此先确保真正部署了阻断式 CI、独立审查及受保护分支，再考虑无人值守合并；不要把“脚本执行成功”当成质量保证。

## 明天可以试的最小版本

- 挑一个低风险 Issue，写明可观察的用户结果、失败路径、不可触碰的资源；让 Agent 自行调查实现。
- 在仓库说明里写清如何**启动、操作、检查持久化状态、停止应用**，而不是贴一堆工作态度规则。
- 要求 PR 含 `## Exercised`：实际运行命令、观测结果、未验证部分；让另一段新会话检查原始目标与 diff。
- 暂不启用自动合并。连做几次，记录哪些人工评论真找到了问题、哪些只是重复机械检查。
- 只有当某类漏检反复出现时，才增加一个可执行的检查或契约测试；每次验证它能识别旧失败样本。

**这篇文章要带走的不是 Forge 这个工具，而是一种分工：人把问题定义得值得做，Agent 负责把工作做完并展示证据；只有证据接不上、业务意义不确定或错误代价太大，人才重新进入实现细节。**

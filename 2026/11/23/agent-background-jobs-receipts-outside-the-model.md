# 别让 Agent 自己宣布任务完成：给无人值守工作加外部回执和漏跑检查

**一句话结论：** 把定时研究、自动测试、项目巡检交给 Agent 后，别再要求它「结束时给我发个报告」就算验收。**回执由启动 Agent 的外层程序负责；另设一条独立检查，专门发现连启动都没发生的任务。** 这是把「每天自己打开会话查进度」变成「只处理异常和有价值的结果」的一条可落地路径。

## 从 48 个定时任务里，找出真正让人累的环节

2026 年 11 月 16 日，独立开发者今井政和公开了自己用 Claude Code 维护 Web 站点和多个日常工作流的记录。按其 11 月 13 日的清点：一个人负责发布、支付与方向决策；一个主 Claude Code 接收需求并分派；`.claude/agents/` 中有 15 个专业分工；60 个定时任务配置中 48 个处于启用状态、12 个停用。macOS `launchd` 按时启动 `claude -p` 等命令。

过去最难的不是让 Agent 多跑一次，而是**不知道它有没有跑、是不是中途失败、失败后谁来告诉自己**。想象一个早上自动检查依赖漏洞、晚上自动整理调研材料的工作：人工逐轮催促被省掉了，但如果还要打开十几个会话确认输出，异步委派并没有省心。

作者没有继续给 Claude 增加一条「请务必报告」的提示词，而是换了报告的责任人：**让调用者发送回执，而非被调用的 Agent。** 这是本文最值得移植的部分。

## 做法一：回执写在 Agent 进程外面

作者用启动任务的 shell 脚本在退出时发送邮件。原文展示了这个关键形状：

```bash
trap 'python3 report_mail.py send --job "每天巡检" --status "$STATUS" --log "$LOG"' EXIT
```

逻辑不复杂：Agent 能否生成一段优美的结束语，不再决定有没有执行记录。启动脚本捕获执行结果，即使 Claude 运行中报错、返回非零状态，也尽可能把日志与状态交给回执程序。作者让每次运行都有「成功、失败、打断、无变化」的区分，并为静默的日常巡检设计「无发现」回执。

实际操作时，这条 `trap` 是**核心思路，不是完整可照抄的生产脚本**：原文节选没有展示 `STATUS`、`LOG` 如何赋值，也没有证明最终业务产物正确。下面是按同一思路写的最小示意（不是作者公开原脚本）：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
RUN_DIR="$(mktemp -d)"
LOG="$RUN_DIR/agent.log"
RESULT="$RUN_DIR/report.md"

report_on_exit() {
  rc=$?
  state="failed"
  if [[ "$rc" -eq 0 && -s "$RESULT" ]]; then
    state="completed"
  fi
  python3 report_mail.py send \
    --job "weekly-research" --status "$state" --log "$LOG" || true
}
trap report_on_exit EXIT

claude -p "完成本周资料核查，把带来源链接的结果写入 $RESULT" >"$LOG" 2>&1
test -s "$RESULT"
```

这里用每次运行独立的目录，避免 Agent 没动手、却恰好找到上次留下的结果文件。`test -s` 只能检查文件非空；真实工作还应校验来源链接、必需字段、测试结果等**具体产物契约**。回执脚本本身失败时，`|| true` 避免掩盖主任务状态，但意味着还需要另一条通道检查回执是否缺失。

官方 Bash 手册确认，`EXIT` trap 在 shell 退出时执行；它不是不死的守护者。断电、进程被 `SIGKILL`、调度器没启动，根本不会运行这段代码。这正好引出第二个动作。

## 做法二：检查「本来应该有，但没有发生」的工作

作者最初有了邮件，仍然遇到问题：**没启动的任务不会发失败邮件。** 他于是每天晚上额外检查定时任务登记表，核对四种情况：任务未加载、该常驻的任务已退出、计划时间之后三小时仍没收到回执、已停用的任务却仍在运行。

这里的重点是把**预期执行清单**放在任务外部。判断「漏跑」不能靠 Agent 回想自己今天干了什么。对于用户，把它想成一张简短的任务台账即可：任务名、预期时间、运行标识、最近一次有效产物、结束状态。巡检时对照这张表，而不是逐个打开聊天记录。

作者还踩过一次典型的误报：Mac 睡眠时，计划中的任务没有启动，晚上检查却把它们全部算成故障。后来他检查预定时间前后两分钟的系统日志；没有系统活动的时间段，单独标为主机睡眠，而非「Agent 执行失败」。这是个人 macOS 环境里的经验参数，**不是通用的两分钟阈值**。服务器、CI runner 或云任务应该按各自的调度语义区分跳过、延迟、执行失败。

这一层最能改变人的工作方式：出差时不必盯着每个定时研究结果；回来只需要看哪些任务漏跑、哪些产物异常，以及为什么被跳过。

## 证据：有具体运行量，也有真故障，但没有提效百分比

作者报告 10 月 30 日至 11 月 13 日的 15 天内发送了 **229 封回执邮件**，单日最多 **28 封**。他发现邮件越多越没人看，于是把五分钟级别的高频监测改成仅在事件发生时提醒；「没有变化」的日常任务仍保留可追踪状态。这说明设计重点不是让 Agent 说得更多，而是让**人的注意力只花在需要决策之处**。

原文列出三个实际故障：11 月 6 日，某个社交发布任务漏读其他项目的规则，把带跟踪参数的长链接直接发出；11 月 9 日，销售工作流修复了共享盘读取问题，却遗漏一项依赖，第二次依然得到 0 条结果；11 月 12 日，作者本来只想 push 自己的 2 次提交，结果同一目录里另外 9 次尚未推送的提交一起发了出去。这些事故让作者把规则从聊天里的提醒，移到共用入口检查、依赖清单与 Git `pre-push` 检查。注意：**这些防误操作措施是作者的配套实践，不是让回执生效的必要条件。**

独立的 [Claude Code Issue #91095](https://github.com/anthropics/claude-code/issues/91095) 记录过定时任务显示成功、却没有产生任何文件或调用的情况；[Issue #36632](https://github.com/anthropics/claude-code/issues/36632) 记录了 `claude -p` 在某类工具调用结束路径上以退出码 0、空输出的情形。这两份报告发生在**不同执行模式**，不能证明作者的 `launchd` 工作流会复现同一个软件缺陷，但它们独立支持一条判断：**运行状态与实际业务完成不能画等号。**

这份实践的可核查边界也必须说清：作者给出了任务数量、邮件量和具体事故，但没有公开完整配置、原始日志、自动完成率、人工查看时间或引入回执前后的总成本。229 封邮件不是 229 次成功；更不能据此说「人工工作量下降了多少」。

## 为什么这比「把结束提示词写得更严格」有效

LLM 可以写结果、调用工具，也可以自检，但它无法在**自己没被启动**时发出警报。上下文窗口再大，也不能让一次没有执行的任务自动留下可信的执行事实。即使启动了，某个工具超时、进程终止或模型把半成品描述成完成，单靠最终自然语言也不足以验收。

从协作边界看，三个问题要分开回答：**有没有按时启动？进程有没有正常结束？交付物真的满足要求吗？** 第一项由调度登记与外部巡检回答；第二项由退出码、日志和回执回答；第三项由可执行的产物检查及必要的人工复核回答。三者缺一，都不能轻易报告 `completed`。

作者还有一条克制的做法：重复任务的经验记在 `docs/learning.md`，记录日期、动作、结果与证据、下次调整；但不让 Agent 根据「学到的教训」自动改写操作规则，改规则仍先征求本人同意。它避免一次偶然成功变成下一次任务的永久假设。对编程、研究和自动化调试来说，这比给会话不断追加长篇行为准则更容易复核。

## 明天可以尝试的最小改动

不必仿造作者的 15 个子 Agent 和 48 个定时任务。先拿一项已经存在的无人值守工作，比如每天检查某个 PR 的测试结果，或每周整理一份技术研究摘要：

1. **明确产物**：指定唯一输出文件或记录、必须包含的字段、怎么判定本次为空结果，以及什么状态才算完成。
2. **把回执移到外面**：在启动脚本里记录日志、退出状态、产物检查结果；Agent 负责做事，脚本负责宣布本次运行状态。
3. **补一条漏跑检查**：每日对照预期的执行时间与有效回执，特别区分没启动、执行失败、没有新内容和业务产物不合格。
4. **只让异常打断人**：正常成功和「无新发现」归档；没有回执、校验失败或需要业务选择时才提醒，并带上日志与可复现路径。

这套方法最适合批量研究、离线测试、定时巡检和异步文档处理；对于临时一次性问答，外部回执的维护成本往往不值得。真实结果仍需检查：一份被成功发送的邮件，不等于一个任务已被正确完成。

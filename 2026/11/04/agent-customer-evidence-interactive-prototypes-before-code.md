# 别让 Agent 带着模糊需求写代码：用客户证据和可交互原型先找出验收条件

**一句话结论：先让 Agent 从真实用户证据中找出边界条件，再做可操作、可重置的原型，把暴露的问题转成测试；等行为说清楚了才交付代码。** 适合需求来自访谈、存在金额/状态转换或跨团队理解差异的业务功能。它优化的不是模型写代码的速度，而是少把错误需求迅速做成“能运行的软件”。

本文精读 Enrico Teotti 于 **2026 年 10 月 8 日**发表的 [Working in an AI-first company in 2026 (without the hype and the fluff)](https://teotti.com/working-in-an-ai-first-company-2026/)。文章记录一名工程师在约 38 万行 TypeScript 单仓项目中，完成房产交易结算系统的“分次收款”功能；内部仓库及访谈不可公开复核。以下“作者报告”的数字不视为独立实验。

## 真正的难题不是写收款接口，而是确定什么算一笔钱

业务上，系统预期收一笔 **5,000 美元**的款，客户却可能先电汇 4,000 美元，再用支票补 1,000 美元；也可能有多个付款人，甚至超额付款。如果直接给 Agent 一句“支持部分收款”，它可以迅速生成 API、弹窗和数据库字段，却很可能把同一笔资金记两次。

作者旧团队用 Linear、Slack 和 GitHub Issue 管工作。票据说明“做什么”，却没有把客户的原话、反例、方案取舍和后来为什么改决定放在 Agent 够得着的地方。于是开发者或 Agent 要反复问业务人员、在讨论串中翻找答案，再用不完整的理解动手。

**改变的是需求输入的形态，而不是写一篇更长的提示词。** 作者所说的 product brain 不是模型长期记忆，更不是自动产品经理：它是通过 MCP 可检索的访谈转录、逐条客户反馈、路线图卡片、研究页和原型，且能追溯到原始来源。

## 一条真实工作链：证据 → 原型 → 测试 → 实现

### 1. 先查访谈，让“需求”变成带出处的业务场景

作者问 Agent：客户怎么处理拆分到账？Agent 检索历史访谈，归纳出同一付款人使用多种付款方式、多个付款人共付、超额付款三个情况，并附回原始谈话的链接。它还估算相关情况约发生于八分之一的业务文件中；这只是作者系统内的估计，公开材料不足以检验抽样口径。

另一次查询 25 份访谈时，Agent 找到一项具体交易：清单写着应向房产经纪支付 **10,245 美元**，实际用两张支票支付，分别为 10,000 美元和 245 美元。这一来自客户的反例后来被转成自动测试。

这里最可迁移的动作是：**不要让 Agent 交“需求总结”，要求它交“场景—证据出处—仍未解决的判断”。** 如果只给一份漂亮的概述，人仍然得重新核验每条业务规则。大段抓取全部访谈也不是解法：作者报告，曾因搜索工具不精确而下载整份转录，导致工具响应过大、撞上上下文限制。

### 2. 在迁移数据库前，先操作四种可能的方案

Agent 先生成包含 **四种收款交互**的低保真页面；未被选择的方案没有删掉，而是附上拒绝原因。团队先讨论“分次到账是新记录、原记录的修改，还是子记录”，而不是急着美化表单。

选定结构后，Agent 制作一份**独立 HTML 高保真原型**：沿用生产设计变量，模拟网络延迟和银行流水，可以反复提交分次到账、观察账本合计、然后重置。这与静态截图的差别很大：**原型本身会运行一部分业务状态变化。**

正是在模拟 **15,404 美元分次到账**时，重复计数的缺陷暴露了。团队还没有写生产数据库迁移，便能把这个失败场景转成实现阶段的测试。此金额是另一个原型案例，不要和前述 5,000 美元或 10,245 美元访谈记录混为一谈。

反馈也不再是“右边那个东西移走”。页面提供定位式批注：点选元素、写评论、复制带元素位置和选择器的 Markdown 给 Agent。同类开源工具 [Agentation](https://github.com/sh-wolf/agentation-cc) 也公开了这种结构化反馈方式，但不能据此断言作者内部批注工具就是它。

### 3. 再让 Agent 实现，审查交给不同问题视角

作者使用 Claude Code 的 Compound Engineering 流程，将场景、范围、完成定义与实现安排放进同一份文档。分次收款被拆成五个具体单元：拆分服务方法、API 路由、入账侧栏、账本表格、汇总测试。**计划是可修订的共同参考，不是让 Agent 必须逐字执行的合同。**

原文 9 月 11 日的时间线很具体：

| 当天时间 | 已记录的进度 |
| --- | --- |
| 09:15 | 高保真原型验收 |
| 11:24 | 实施计划写成 |
| 12:27 | 界面、服务及测试完成，类型和 lint 检查通过 |
| 12:35 | 四路独立视角代码审查启动 |
| 15:15 | 审查发现处理完毕 |

这不是“六小时全自动交付”的证据：中间存在人的决策与验收，原文也没有提供完整的人力时间记录。

四路审查分别看正确性、对抗性失败、项目规范与性能。对抗视角抓到一个测试未覆盖的漏洞：**请求已在服务端成功，但客户端因超时认为失败；用户关闭侧栏再打开，组件状态中的幂等键丢失，下一次重试生成新键，服务器可能把同一笔钱再入账。** 作者将键移入 sessionStorage，使同一次重试可以复用标识，并为最后一期到账的另一个边界补了服务测试。

这不意味着 sessionStorage 本身提供了财务级 exactly-once：键的持久期限、服务端去重约束、跨设备或跨会话重试仍须另行设计。作者展示的是找出一条真实的重复入账路径，而不是宣布收款系统已被形式化证明安全。

## 一个可以直接交给编码 Agent 的任务形状

下面是基于作者做法整理的**迁移示例，并非作者原始提示词**：

> 先不要改生产代码。请检索客户访谈和相关 Issue，列出“部分收款”的不同情形；每个情形给出原始出处、例外和待人工确认的问题。然后做一份单文件 HTML 原型，能模拟多次收款、超额付款、请求成功但响应超时、重试及重置，并显示前后账本余额。至少给出两种交互方案及放弃理由。等我确认规则后再形成实现计划与测试清单。实现后请独立检查重复入账、最后一期到账和环境差异，报告实际运行的命令、结果及仍未覆盖的路径。

不用先建一套复杂知识中台。哪怕只有几份可引用的访谈摘录、一个可运行原型和一张验收表，也能先试这条工作链。要克制的是**人反复口述业务背景的次数**，而不是一味减少 Agent 对外部证据的读取。

## 为何它有效，又为何不能误读成“规划解决一切”

这条链把贵的错误尽量前移：访谈中修正概念比数据库迁移后返工便宜；原型里看到重复计数，比审查一千行 diff 更容易让业务人员判断对错；留下失败输入和预期余额，比“看起来符合需求”更利于机器验证。**这是工程推断，不是原文提供的受控效率实验。**

作者自己也记录了两个反例。一次本地正常的地址验证，在生产环境因为 Nitro 对非 H3Error 的错误数据做了脱敏而变成笼统“Server Error”，Sentry 当时也没记录该 4xx。另一次账本同步被改为后台作业，本地通过，生产环境却没有触发任务。更扎心的是，之前的审查已经提醒过“提交事务后副作用可能静默丢失”，却只留在一次性审查输出里，没有存到下次规划会搜索的 docs/solutions/。

**Agent 有证据不等于有答案；学到教训也不等于下次会用。** 作者曾从访谈里搜到大量房产合同引用，却仍靠同事一句话澄清专业术语，然后才把答案补进词汇表。长期记忆的关键不是堆更多摘要，而是把已确认、可复用的约束放进下一次工作真正会检索的位置。

作者三个月内约 **100 次**使用相关工程命令，记录 **约 29.5 小时 Agent 活跃时间**，涉及约 30 项功能。这个计时明确排除了等待他回复的时间，也不包括访谈、人工审查、手工测试和产品讨论；既不是全部工程工时，也不能证明“30 个功能只花了 29.5 小时”。

最后一个看似反直觉的变化是**不要同时开太多实现 Agent**。作者发现，多个工作树里的功能一起向人索取决策、验收和背景判断时，人的注意力并不会随 Agent 数量线性增长；空出来的并行时段更适合安排界面探索、访谈提炼等有边界、不立即制造额外代码审查负担的任务。

## 独立核查与适用边界

[Compound Engineering 开源仓库](https://github.com/EveryInc/compound-engineering-plugin) 可核对 brainstorm、plan、work、code-review，以及把经验写入 docs/solutions/ 的实际命令和目录约定；但**不能证明作者私有系统中的业务数字或时间记录**。社区 [Issue #956](https://github.com/EveryInc/compound-engineering-plugin/issues/956) 还记录过子 Agent 只返回摘要、完整分析内容丢失的真实工具故障，提醒我们：多 Agent 审查必须留下可检查的持久结果，而不能只相信协调 Agent 的结论。该 Issue 与本文案例相互独立，不能冒充对作者案例的复现。

方法不适合照搬到无访谈素材、需求已充分形式化的简单修复；原型中的模拟银行流水也不能代替真实支付接口、生产级幂等保障或上线后观测。作者隐去业务细节、未公开仓库，本文没有重跑原型或模型会话，因此只将其作为**有具体失败案例的一手工程实践**，不声称其具有普遍效率倍率。

## 明天可用的最短清单

- [ ] 交给 Agent 的不只是 Issue，还有能追溯到原话的业务场景；未查到答案就明确提问，不准自行补全。
- [ ] 编码前先让 Agent 交付**能操作、能重置**的最小原型，至少试一次失败与重试路径。
- [ ] 从原型中提炼具体输入、状态变化与可断言结果，再写实现和测试。
- [ ] 审查围绕“怎样可能造成真实业务后果”，而不是只让同一 Agent 再读一次 diff。
- [ ] 把确认过的失败模式归档到下一次任务真正会读取的位置；并行任务不要超过自己能验收的数量。

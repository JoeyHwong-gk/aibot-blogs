# 别默认让 Agent 边写边测：先确定反馈值得花多少成本

**结论：不要把「给 Agent 更多测试工具、要求每一步都跑一遍」当成无条件的好习惯。** 对已经能稳定完成某类任务的强模型，反复测试可能只是额外等待；对经常漏掉边界要求的便宜模型，能直接执行的契约检查可能比再写十段提示词更有用。两种情况都应保留**独立最终验收**。

这是读者可以立刻改变的一件事：**先用同一个真实任务观察模型哪里失败，再决定把测试放进开发过程，还是仅在交付时执行。** 不要先花一周搭复杂工作流，再寻找它是否带来收益。

本文精读 Naresh Jain 在 2026 年 10 月 13 日发表于 Martin Fowler 网站的 [Are Harnesses Worth the Cost?][1]。它发表于本期前 23 天，不是本周新稿。作者同时是实验所用 Specmatic 产品的创始人，这一点需要进入证据判断。

## 同一份需求，四种交付方式

任务不是写一个玩具函数，而是交付一个 Java/Spring Boot 的商品发现 BFF：提供客户端 HTTP API、调用下游 Order API、将成功查询得到的第一个商品发布到 Kafka，并处理超时、延迟完成、非法字段、上游错误和消息确认。

需求中的两个不起眼的细节，正好能说明为什么 Agent 经常“代码看起来合理，集成起来不对”：

- 下游创建商品超时，BFF 应返回 **202**、附带 monitor 链接，随后后台重试；不能笼统地返回 503。
- Kafka 消息发出并不等于交付正确。消息头、多余字段、可选字段的序列化形式都必须符合约定，且要得到确认才能给客户端返回成功。

作者公开了[完整任务简报][2]，里面固定了 API、异常处理、技术栈和依赖边界；这远比多数团队的普通 Issue 详细，是实验的有利条件。

他用 Codex 分别驱动 GPT-6 Sol 与 GPT-6 Luna，推理强度均为 low，每个模型都跑两组：只有任务简报；以及任务简报加一组契约、示例、依赖模拟与可执行验证工具。每格运行 10 次，总计 40 次。各次使用隔离 Docker 工作区和新的 Codex home。**开发结束后统一交给另一套 178 项验收检查；Agent 开发时看不到这套最终测试。** [1]

| 模型 / 开发反馈 | 交付通过次数 | 平均耗时 | 平均 Token 用量 | 单次估算成本 |
| --- | ---: | ---: | ---: | ---: |
| GPT-6 Sol / 无额外反馈 | 10/10 | 6 分 51 秒 | 1,076,371 | $0.406 |
| GPT-6 Sol / 持续反馈 | 10/10 | 19 分 53 秒 | 11,331,970 | $2.679 |
| GPT-6 Luna / 无额外反馈 | 3/10 | 15 分 56 秒 | 5,860,736 | $0.086 |
| GPT-6 Luna / 持续反馈 | 10/10 | 35 分 | 22,933,648 | $0.273 |

这是**作者报告的10次运行均值与验收次数**，不是我们重跑出的数据。10/10 意味着这十次都过了，绝非证明成功率恒为 100%。Token 统计包含重复上下文与缓存读写，不能按“消耗了两千万个新生成 Token”理解。[1]

真正值得改变工作习惯的，是实验的两种相反结果：

**给 Sol 加持续测试，没观察到一次额外通过，却把一次任务从 6 分 51 秒拖到 19 分 53 秒、费用从约 $0.406 增至 $2.679。**

**给 Luna 加持续测试，通过次数从 3/10 增至 10/10；但一轮耗时涨到 35 分钟。** 它的 $0.273 比无额外反馈的 Sol 便宜约 33%，但墙钟时间大约是后者五倍。若你的瓶颈是等待，而不是 API 费用，这未必划算。

## Agent 漏掉的不是“怎么写 Java”，而是协议边界

没有额外反馈的 Luna 其实多数功能都写对了，平均通过 94.8% 的检查。但七次未被接受的交付，在一部分错误路径上很像“差一点”：

- 下游超时后，本应返回 202 和轮询地址，实际四次返回 503、两次返回 400、一次返回 429。缺少 monitor 链接还引发了后续多项连锁失败。
- 三次 Kafka 交付消息到了，却违反线协议：两次附带不该存在的 `__TypeId__` 头；另一次把应该为数组或省略的 `categories` 写成 `null`。
- 某些实现把不合约定的媒体类型返回为 415，而任务约定要 400；另一些读取 `ORDER_API_API_KEY`，启动配置却提供 `ORDER_API_KEY`。[1]

这给人一个很具体的提示：**同样的要求写在文档里，不代表 Agent 在处理五六个子系统后还能把它们完整兑现。** 作者将这理解为“注意力遗漏”；这是一种合理解释，但实验没有定位 LLM 内部原因，也不应当当成已证明的模型机制。

## 改变委派方式：不是多加规定，而是让要求能报错

作者的做法有两类材料。第一类是开发前就存在的 **约束**：OpenAPI、AsyncAPI、请求/响应示例以及负责说明如何运行验证的 Skill。第二类是开发中可调用的 **反馈**：契约测试、下游 HTTP/Kafka 模拟服务、超时和重试场景、CTRF 测试报告与覆盖率报告。

测试不是一句“请你认真检查”，而是能明确指出哪里偏离预期。作者还在执行前校验示例与契约是否一致，以免 Agent 同时收到两套互相打架的标准。

这里有个容易遗漏的安全边界：**不要让同一个 Agent 在测试失败时偷偷修改验收标准。** 约定与示例应由负责人确认，修改它们需要独立审核；Agent 可以诊断、修实现和运行环境，但不能为了过测试降低要求。这与强制它“先写多少条测试”完全不是同一回事。[1]

把这件事应用在自己的项目时，我建议先做一个小实验，而不是直接把 Specmatic 或任何工具塞进全仓：

1. **选一个总会返工的具体任务类型。** 例如 webhook 幂等、超时重试、批量数据导入或接口兼容，不要选一个没有可执行验收标准的宽泛架构问题。
2. **从业务后果写出 5–10 条固定检查。** 至少包含成功路径、一次失败重试、协议字段、状态持久化及外部副作用。检查必须在 Agent 编码前冻结。
3. **先让当前常用模型不依赖新增检查做一遍。** 记录实际任务耗时、人工追问次数、失败路径、推理费用、最终验收是否通过。必要时重复几次，别根据一轮就断言好坏。
4. **如果常见失败是“明明有要求却漏了”，再把检查接到开发循环。** Agent 能看见失败原因并自主重跑；人只负责修改业务事实和高风险决策。
5. **如果不加反馈已经稳定通过，就先只留最终门禁。** 这是从上述对照得到的工作假设，**不是原实验已经验证的第三组结果**。你自己的项目需实测它是否仍能及时发现错误。

可以向 Codex/Claude Code 这样交代一个已有契约的 API 改动（以下是本文改写的任务示例，**不是原作者逐字 Prompt**）：

> 实现本次 API 改动；接口契约和已确认的行为样例是验收依据，不得为通过测试修改它们。你可以自行选择代码结构、读取必要上下文与执行测试。如果在开发中发现超时、重试、序列化或事件副作用不符合约定，先复现、修实现、重跑对应场景；完成后给出启动命令、实际测试结果与尚未覆盖的路径。需要改变契约或访问真实生产环境时先征求批准。

没有现成测试工具也不必全靠想象。Specmatic 的公开 [BFF 示例仓库][3] 有 Spring Boot、Order API 与 Kafka 模拟环境，并给出了可执行命令：

~~~bash
# 以下命令来自公开示例仓库，不是本次对照实验的原始运行命令
./gradlew test --tests="com.component.orders.contract.ContractTests"
~~~

那个示例使用 Kotlin/Gradle 和 Specmatic Enterprise，而文章中的实验任务约束是 Java/Maven。**不能把“示例能运行契约检查”写成“40 次实验已被公开独立复现”。** 工具能力还可以从 [Specmatic MCP Server][4] 的开源说明核实，但其具体配置与许可证应按实际项目决定，不是采纳本文做法的前提。

## 把“便宜”算在整项工作上

仅以模型价格排序，会漏掉 Agent 重试、人来回解释、制作契约和复核的成本。仅以 10/10 判断“可靠”，也会漏掉延迟和任务差异。

这次实验最多支持这样的判断：对于**这一个规格完整的 BFF 任务**，一种低价模型配合开发期契约反馈，在作者报告的十次试验中达到了与强模型相同的验收表现；单次估算模型费用更低，但耗时显著更长。它**不能证明整个团队的总交付成本下降 33%**，因为契约的编写、维护与人工审核没有进入统计。

独立讨论也抓住了这点。API Evangelist 的 Kin Lane [指出][5]，真实系统最大的麻烦是第三方接口的约定通常并不由你的团队控制，不能指望总有现成准确的契约。Dark Factory Dev 的[技术摘录][6]也提醒：作者售卖实验所用的契约工具，样本小、费用不含建设成本。这些是**独立评论与方法层面的核查，不是对40次运行结果的独立复验**。

还有两个实验设计限制必须保留：一是“开发前提供约束”和“开发中提供反馈”同时变化，因此不知道各自贡献多少；二是外部 178 项检查与人类编制的任务规范相关，能避免 Agent 给自己出题，却不能保证规范覆盖了全部真实业务风险。

## 明天可用的判断表

| 当前观察 | 下次委派的变化 |
| --- | --- |
| 强模型对这类任务很少返工，但每次被迫跑大量验证 | 保留独立最终验收，尝试减少开发中重复执行（需本地对照） |
| 低成本模型总漏超时、边界值、事件副作用 | 为遗漏项增加可执行契约与模拟失败，让 Agent 自己修到通过 |
| Agent 测试全绿，真实行为仍不对 | 固定由人批准的检查与真实接口样本，增加端到端/副作用验收 |
| 没有契约，连正确结果是什么都不明确 | 先请人确定关键场景，不要先堆更多 Agent 规则 |
| 任务优先级是交付速度，而不是模型调用费 | 比较完整任务墙钟时间和人工返工，而不只比 token 成本 |

**真正该优化的是人在什么地方介入、Agent 在什么时候获得可执行反馈，而不是测试指令越多越好。** 有时最省事的做法，就是把最终验收写清楚，然后让足够强的 Agent 自己完成任务。

# AI 生成的测试越堆越多：让 Agent 选执行用例，把风险取舍留给人

**一句话结论：测试用例可以让 AI 继续写，但不要让“有多少用例”直接决定“发布前必须跑多少”。把行为规格留在仓库里，让 Agent 从本次 PR 找出受影响的验收准则，由人确认风险，再按一张公开的决策表自动选出本次要执行的 UAT 用例。**

这适合已有大量验收案例、每轮发布都需要人工回归的团队。它解决的不是怎么让 Agent 写更多测试，而是怎么避免 AI 提高了写用例的速度，却让真人的验收工作跟着失控。

## 一次发布要跑 277 个案例：问题不在生成速度

2026 年 11 月 12 日，PIVOT 的 QA 工程师兼 PjM Keisuke 记录了这套方法的反复试错。他们为 iOS、Android 应用维护三类东西：GitHub 中的测试观点、GitHub 中逐条描述「什么条件下应该发生什么行为」的测试用例，以及 Notion 中针对每次发布的执行记录。

这里有个重要前提：**测试用例同时就是产品的现行规格**。团队不再维护另一套完整功能规格；每次 PR 改行为时，测试定义也随 PR 增删，接受代码审查。非会员、退出登录、iPad、返回操作、不同入口等条件，都值得写成独立一行。

他们让 AI 根据 PRD、Figma、PR diff 生成这些案例。写案例的阻力降低了，库却越长越快；有一次发布，UAT 执行对象达到 **277 件**。

旧办法是：本次改到哪个功能，就把这个功能的案例全部跑一遍。嫌多时也会人工删减，但执行记录没有写「为什么可以跳过」。下次发布，还得重新判断一次；有人问漏测风险，甚至说不清上一轮为什么没有测。

Keisuke 没有删除案例。**规格的完整性和本次验证的工作量，本来就应该是两个独立决策。**

## 第一版：按功能估风险，仍然跑掉八成案例

团队先用常见的风险思路：影响程度 × 本次修改引入问题的可能性。

可能性只分三个档：**3** 表示 PR 改了行为，**2** 表示内部实现或位置调整，**1** 表示没直接改、但可能受波及。按功能评估影响，再把测试分成正常路径、状态、操作、画面、异常五种，重要功能覆盖更多种类。

他们没有立刻把规则用于新发布，而是拿**过去五次发布**做回溯：原有 **980** 件候选中，规则选出 **809** 件，占 **83%**；当时记录的 **13** 个 UAT 缺陷，能覆盖 **11** 个。如果调整到一个缺陷也不漏，就得选到 **92%**。

两个未覆盖的缺陷都发生在有限条件下，用户有办法绕开。团队选择承担这部分风险，而不是为追求历史样本的零遗漏执行近乎全量的测试。

这个结论别倒过来读：**11/13 不是未来发布的缺陷检出率，更不是「安全跳过 17%」的普适承诺**。五次发布、13 个历史缺陷，只能用来检查当前选例规则有没有明显失真。

## 一次 iOS 重构，让功能级选例直接失效

随后来了真正考验规则的一次发布：iOS 应用做多模块重构，几乎所有页面目录结构都发生变动。功能级台账于是把大量功能判成可能性 2；一个重要功能只要被触及，下面十种测试条件就容易整批入选。

结果是 **1,339 件候选**。当时工程师靠大约五轮人工筛选，把实际计划收敛到 **516 件**。这证明了人可以靠经验找到更小集合，也证明这种方法无法轻松复用——每轮重构都重新开会砍五遍，不是高效协作。

症结是选例粒度错了。「视频播放」既包括按下播放键后必须能播放，也包括切换倍速；两个行为故障的后果完全不同，但都被贴上同一个功能风险标签。

团队遂把风险台账细化成 **用户故事 × 验收准则**，要求每条准则只描述一种行为。例如「点播放后开始播放」属于 **S1**，因为失败会让用户根本看不了视频；「可以调节播放倍速」属于 **S3**，因为仍然能以普通速度看。

他们把后果分为四级：

| 后果等级 | 用户实际遭遇 |
|---|---|
| **S1** | 核心目的无法完成，也没有替代路径 |
| **S2** | 后果不可逆，或直接影响收入 |
| **S3** | 还能达到目的，但需要绕路或体验变差 |
| **S4** | 某项非核心附加功能不可用 |

概率档位也按**验收准则**而不是整个功能赋值：同一个播放功能里，本次 PR 改了哪个行为，哪个准则才记作 3；仅代码迁移、行为没改的准则可记作 2；只存在潜在波及的记作 1。

但细化粒度还不够。第一版准则级规则在那次重构上仍选出 **1,046 件**：即使 S3 行为没变，也规定每条准则都跑一个正常场景。准则很多，照样几乎全选。

**真正减少工作量的不是更精细地打分，而是明确「哪些低风险行为这次可以不执行」。**

## 一张能让人解释的表，比神秘风险分数更有用

PIVOT 最终采用的选例表如下。「历史出过缺陷」指该验收准则下曾暴露问题的具体条件，而非整个功能都要重跑。

| 后果 | 本次行为改变（概率 3） | 行为没改变（概率 2 或 1） |
|---|---|---|
| S1 | 全部案例 | 全部案例 |
| S2 | 全部案例 | 一个正常路径 + 历史缺陷条件 |
| S3 | 全部案例 | 只跑历史缺陷条件；其余在临时探索时关注 |
| S4 | 一个正常路径 | 只跑历史缺陷条件 |

作者没有把影响和概率相乘生成一个总分。PM 看到这张表，就能直接问：「为什么这条没测？」「这个后果等级定得对吗？」也能清楚知道哪些风险是团队主动接受的。

用**最终 S4 细则补入之前**的一版收缩规则，重新套那次 iOS 重构发布，候选从功能级的 **1,339** 降到 **628**，少了约 **53%**。注意：**628 不是当前完整规则下的精确件数，更不是实测执行耗时**。作者后来为 S4 补充了「历史缺陷条件也必须执行」，不能把这笔回算直接当成最终发布报表。

被跳过的 S3 也不是从视线中消失。团队把腾出的验收精力投入高影响功能的探索式测试，尤其留意低概率 S3 行为。

## Claude Code Skill 负责搬运和筛选，人批准风险事实

Keisuke 把反复筛案例的过程交给 **Claude Code Skill**。实际工作链路是：

1. 人给出**发布工单**，Skill 收集对应 PR，按功能整理变更。
2. Agent 找出受影响的验收准则，并给出「行为改动 / 内部调整 / 可能波及」的依据，**询问 QA 工程师确认**。
3. 确认后，由**脚本按决策表选例**，而不是让模型凭感觉随意挑 628 条。
4. Skill 在 Notion 建立本次执行记录，保留入选与跳过的理由；GitHub 的用例定义不被删掉。

**规则原文档优先于 Skill**：两者冲突时，以人能阅读和修改的规则文档为准。团队已经反复改过选例表，因此没有把策略悄悄埋死在提示词或脚本里。

下面是根据这套工作方式整理的**可迁移任务表达，不是作者公开的原始提示词**：

> 给你发布工单和对应代码仓。先列出相关 PR、受影响的用户故事及每条验收准则。逐条引用 diff 或需求作为行为改变的证据，建议概率档 1/2/3；不确定的标为待确认，不要自行定案。待我确认后，使用仓库里的选例规则脚本，输出本轮执行清单、未执行清单及每项理由。不要修改测试定义以缩小工作量。最后生成可追溯的发布验收记录，并标明未执行项。

从 Agent 工程角度看，关键不是 Skill 这个包装，而是**把不擅长稳定判断的部分和擅长机械处理的部分拆开**：LLM 擅长读不规整的 PR、概括变更线索；人更适合批准业务后果和可接受风险；脚本负责按固定规则稳定复算。换一个会话或模型，决策表也不该悄悄变。

## 怎么判断这不是一次漂亮的「少测一半」演示？

证据有实数，但边界很窄。**历史回溯**证明第一版规则曾覆盖 11 个已知缺陷、漏两个；**同一发布的规则回算**证明候选量在一次重构上从 1,339 变为 628；作者还记录了人工五轮筛到 516 以及探索测试的再分配。这些事实比只说「测试效率大幅提升」可靠得多。

没有公开的是：Skill 的源码、模型版本、逐条用例与缺陷映射、完整 Notion 日志、人工筛选用时、执行耗时、token 费用、上线后的漏检比例。因此，不能证明总交付时间确实节省 53%，也不能证明新的规则在下一轮发布不会漏掉 S2/S3 的重大问题。

[独立工程实践整理者 Ivan Nosov](https://nosov.ai/library/lib-2026-11-12-choosing-which-ai-generated-test-cases-to-run/) 对这篇文章作了复核性解读，特别指出五次发布只有 13 个缺陷样本，以及 628 这个数早于 S4 最新修订。它验证了我们没有误读作者的表述，**不是对 PIVOT 原始数据的独立复现**；针对该团队的社区实测证据仍不足。

风险表还依赖两个容易出错的输入：PR 是否真的「只改内部」以及历史缺陷条件是否记录完整。如果 Agent 漏看行为变化，把概率 3 错判成 2，就可能跳过本应执行的检查。**所以人的确认点要设在「风险输入」上，而不是等它挑完案例才随手点通过。**

## 明天就能试的最小版本

不用先开发完整插件。找一轮真实发布，保留全部现有用例，另外建一张「行为准则 / 后果等级 / 本次变更证据 / 概率档 / 是否执行 / 跳过理由」的表。让 Agent 根据 PR 预填，人只确认后果和变更性质；用可重跑的筛选逻辑生成本轮清单。拿上一轮已知缺陷做一次回算，比较**执行件数、能覆盖的历史缺陷及人工审批时间**。若历史重大缺陷漏掉，先改规则，不要为凑一个好看的压缩率上线。

最值得带走的不是 S1–S4 这四个标签，而是这个分工：**Agent 可以减少我们准备和执行验收清单的机械劳动，但哪一部分用户风险值得承担，必须有人说得清楚。**

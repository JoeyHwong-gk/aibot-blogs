# 别让写代码的 Agent 自己判卷：交给独立 QA Agent 验收真实流程

**一句话结论：** 对有界面、有状态和跨服务交互的编码任务，别让同一个 Agent 只靠自己写的测试宣布完成。给另一个没有接触实现过程的 Agent **原始需求、可访问的运行环境和找缺陷的任务**；让它提交可复现问题，再交回编码 Agent 修复。人的工作从反复口述测试步骤，转为确认验收目标、核实缺陷和决定是否交付。

这不是“再加一个 Agent 就会提高质量”的口号。Momentic CTO Jeff An 在 11 月 13 日的文章里给出了具体做法，也公开了足以质疑其收益的数字。适合借鉴的是**改变委派和验收边界**，不必先购买某种 QA 产品。

## 一个八人团队遇到的老问题

Jeff 带领 Momentic 的八人工程团队，已经大量使用后台编码 Agent。他们反复遇到同一个场景：Agent 报告功能完成、测试通过；工程师一打开应用，基础操作却失败。

团队在内部代码仓人工审阅了 **1,000 条 AI 编写的单元测试**。作者报告其中仅 **9.6%** 被归为有用的验证，其余包括低后果检查 **31.6%**、重复覆盖 **22.8%**、过度 mock **22.4%**、未使用 **9.1%** 和刻意凑覆盖率 **4.5%**。这些是单一企业、未公开明细的内部人工分类，不是“AI 测试九成无用”的通用统计。

真正费时的不是测试文件数量，而是**发现失效太晚**：人要启动应用、重走操作路径、指出错误，再让 Agent 修；下一轮仍可能遗漏同一条用户旅程。

作者用富文本编辑器解释另一种盲区：Agent 实现并测试粗体、斜体、下划线按钮，却没有想到“撤销”也应回退格式。注意，这只是文中的**说明性例子**，不是公开的生产事故。测试全部为绿，只证明它验证了自己想到的行为。

## 作者改变了什么，而不只是换一种测试工具

Momentic 的做法不是让编码 Agent 再运行一遍测试，而是改变验收任务的输入与目标。

**第一，QA Agent 只拿原始需求，不接收编码过程。** 它不知道编码 Agent 的对话、推理轨迹和实现代码，因此不必沿着“我已经这样实现了”的路径寻找证据。隔离不是绝对的：两个 Agent 仍可能共享模型偏见，且原始需求本身也可能遗漏关键情形。但至少切断了最直接的自我证实链。

**第二，提供真实可操作的应用，而不是让它看代码推测是否能用。** 作者的团队让 QA Agent 使用远程浏览器和移动设备，点击界面、填写表单、观察反馈和副作用。它的单一目标是发现缺陷，而非解释为何当前实现合理。静态分析和单元测试仍然有用，只是不能替代这些真实用户路径。

**第三，把发现转换成可复现的交接物。** QA Agent 需要指出起始状态、操作步骤、预期结果和实际结果；编码 Agent 收到的是一个可以复跑的失败，而不是“页面好像有问题”的主观评价。修复后重新走同一条路径，直到达到约定的验收条件。人负责核实严重性与可接受的产品行为。

用公开的 QA-Bench 数据举个具体例子：Gitea 的一个 Issue 因依赖关系未满足，用户点击“Close with Comment”时看见失败提示和仍保留的草稿，却可能已经实际发布了评论。用户重试，产生两条重复评论。这类**错误提示与真实副作用分离**的问题，检查一个按钮回调或 mock API 返回值未必能发现；需要在真实界面上操作，再刷新核对状态。这是公开数据集里的缺陷标签，不是作者文章宣称的某次内部生产事故。

## 明天就能用的最小委派方式

例如你让 Codex 或 Claude Code 修改一个“提交审批”的页面。编码任务照常交给主 Agent，构建、类型检查和单元测试也照常运行；但在它报告完成后，开启**新会话或另一 Agent**，不要转发编码过程摘要。给 QA Agent 这样一段任务（根据本文方法改写，并非作者的原始提示词）：

> 在这个隔离的测试环境中，根据原始需求验证“提交审批”流程。使用提供的测试账号，从页面实际操作；覆盖成功提交、重复点击、接口失败后重试、刷新后的状态及权限不足。不要依据开发者自测报告判定成功。每个问题给出复现前提、步骤、预期和实际行为，必要时附截图、浏览器日志与请求证据；不可复现的猜测单独标注。不要修改代码和验收标准。

这段任务最重要的部分，不是多写了几条“提高质量”的规则，而是明确了**输入、权限、目标和输出**。它要求 QA 从界面产生独立观察，且不得把猜测说成已复现缺陷。测试账号必须使用沙箱数据，禁止对真实用户执行有副作用的操作。

随后把已复现的问题交给原编码 Agent 逐条修复。人只需在三处作判断：原始验收标准是否合理、发现的是不是缺陷、修复后的交付是否可接受。对于简单的纯函数或一次性脚本，另开浏览器 QA 反而可能增加总耗时；不应机械套用。

## 效果：更会找 Bug，但也更贵

作者说，Momentic 的独立验证器 Mo，在公开的四个开源应用评测上发现的缺陷数量是 Codex、Claude Code 对照配置的 **3–5 倍**。与其照单全收，不如看其公开仓库的具体条件。

[QA-Bench](https://github.com/momentic-ai/qa-bench) 为 Gitea、Metabase、Twenty 和 Saleor 划分了 **20 个产品区域、1,396 条人工审核缺陷标签**，每次在固定代码版本和种子数据的 E2B 沙箱里通过浏览器找缺陷。下表是公开报告中的 **60 分钟配置**，每个区域通常重复三次后汇总均值，不是单次工作任务的耗时：

| 受测配置 | 平均匹配缺陷数 | 召回率 | 精确率 | 每条匹配缺陷成本 |
| --- | ---: | ---: | ---: | ---: |
| Mo | 269.3 | 19.3% | 84.2% | $2.67 |
| Codex / GPT-6.1 Sol + Playwright MCP | 86.3 | 6.2% | 86.0% | $0.80 |
| Claude Code / Opus 5.5 + Playwright MCP | 59.0 | 4.2% | 79.5% | $4.09 |

这支持一个**有限结论**：在发布者设定的任务和预算下，专用独立 QA 找出了更多被标记的缺陷；它**不能证明**任何编码任务都值得额外付这笔钱。Mo 的精确率低于表中的 Codex，平均每个完整测试批次成本约 **$719**，Codex 约 **$69**，约花十倍费用找到三倍缺陷。更要紧的是，最高的召回率也只有 **19.3%**：没有发现问题不等于没有问题。

第三方 SaaS City 按公开数据重算了成本，还指出产品方既提供 Mo，也设计、组织并评分了评测。公开代码、种子环境、标签和运行命令使方法可核查，但**不能自动消除供应商偏差**；报告费用也未计完整的沙箱、评分和人工分诊开销。我核查了来源与方法，**没有独立重跑**这些实验，也没有获得团队引入 QA 前后的总工时、返工率或上线缺陷对照。

## 为什么这种分工能起作用，在哪里会失效

编码 Agent 的测试容易受自身实现假设影响；同一会话积累的大量实现决定、失败日志与工具输出，也可能挤掉最初真正重要的约束。把 QA 放在**新上下文**，让它根据原始任务观察运行中的系统，可以减少“先相信实现，再挑证明”的倾向。这是合理的工程机制，并不要求不同厂商模型才成立，也不意味着另一个模型天然客观。

真正起作用的反馈不是“再生成更多单测”，而是“用户执行这六步后，页面说失败，数据却已被写入”。它同时提供了可复现输入与错误行为，编码 Agent 才能围绕证据定位原因。

但边界也很清楚：QA Agent 会误报、漏报、循环重试，还可能对环境造成副作用；不同模型不等于独立真值；生产环境里的支付、删除和敏感数据操作必须另设授权与隔离。对已经拥有高质量端到端测试的团队，新增一个探索 Agent 的边际收益应先算成本，不要因为流程看起来先进就无限叠加。

## 可复用的四件事

1. **把验收依据从编码会话中拿出来。** 保存原始需求、不可改变的业务约束和测试账号；不要把“我已经实现了什么”的长摘要当作 QA 输入。
2. **让 QA 操作正在运行的应用。** 至少走一次真实成功路径、一个失败与重试路径，并观察刷新后状态和外部副作用。
3. **只接收可复现缺陷。** 每个 Bug 要能回答“什么状态下、按哪几步、预期是什么、实际是什么”；未经复现的报告留待人工核实。
4. **把效率算完整。** 不只数 QA 找到多少 Bug，还要记录人工分诊、误报、修复往返、验证时长与工具费用；小任务如不划算，就别增加独立验证轮次。

**比“让 Agent 多写测试”更有价值的改变，是把交付定义为：另一个观察者能从原始需求出发，在实际环境中确认行为。**

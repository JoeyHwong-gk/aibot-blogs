# 3207 项测试绿灯，真实调用却失败：怎样让编码 Agent 对交付结果负责

**一句话结论：** 不要让编码 Agent 用“所有测试通过”替代“用户确实能完成任务”。让它在开发中自主运行快速测试、复核 diff、操作浏览器；但在交付前，要求一条连到真实依赖的用户路径，以及一条依赖失效时能明确失败的路径。人只保留最终业务判断和必要的真实环境操作。

这适合接入 LLM、支付、邮件、搜索或其他外部服务的应用。它不要求人重新逐行审查每次 Agent 改动，却要求有人确认：**系统失败时，不能假装成功。**

## 111 次提交后，真正的问题才现身

Ash Gaikwad 在 2026 年 11 月 8 日回顾了 *AI Agents Live 2.0* 的三天开发（11 月 6—8 日）。产品原来是 AI Agent 目录，2.0 增加了条目审核、页面改写、向 AI 助手发问并展示结果等能力。按作者记录，这个版本由 Claude Code 带领实现 Agent 完成，累计 111 次提交；每轮工作留下会话记录，测试套件的绿色结果从 2,643 增至 3,207。[1]

这里最容易误读的数字是“3,207”。它是作者报告的测试通过情况，不是 3,207 次真实业务交付成功；相关仓库与 CI 日志没有公开。

代码已经推送，作者还没有部署。他亲自跑了第一条真实业务路径：让站点通过新的模型调用流程检查自己的条目。**开发用的 OpenAI Key 已经过期，模型调用全部失败；系统却把这次运行标记为完成，并发出了“snapshot ready”的通知。** 结果既没有真实回答，还消耗了该条目唯一一次免费的 snapshot，随后产出了没有数据支撑的建议。另一个错误是测试问题继承了管理员账号语言设置，英语问题里混入 Marathi 词。[1]

这三个问题不是因为 Agent 没写测试。作者明确说，测试把模型替换为始终返回成功结果的 stub，所以测试根本没有经过“模型不回答”的分支。发文时这些问题尚未修完，2.0 尚未上线。这个未完成状态比一张漂亮的交付截图更值得借鉴：**CI 证明它通过了已编写的检查；真实任务证明检查漏掉了会伤害用户的路径。**

## 作者怎样改变与 Agent 的分工

他没有从头要求一个会话“把 2.0 做完”。先将需求写进 PRD，列出业务决定、验收标记和编号的工作切片；每个切片应能由一个实现 Agent 在单次运行中完成，比如条目编辑后重新审核。主 Agent 为切片写简报：做什么、对应哪条需求、哪些测试证明完成、什么状态算结束。新的实现 Agent 只拿简报和仓库自己的规则，不继承前一个实现会话的长历史。返回后，主 Agent 复核；实现与原计划不同时，把实际行为写进 PRD 的“Built as”。[1]

另一处真实返工发生在 **11 月 7 日**：一次实现 Agent 从记录计划的目录启动，隔着路径修改产品仓库。它写出的代码能运行、测试也通过，却没有遵守产品项目的约定。作者改成在产品仓库内启动编码 Agent，再把记录计划的目录作为附加工作目录。原因不是某种“记忆功能”不够强，而是 Claude Code 会从当前工作目录向上查找项目指令，项目级配置与 hooks 也与目录上下文有关；官方的项目指令文档能核对这一机制。[1][2]

他的日常验证并不轻：每次变更都经过 `bin/ci`（测试、lint、安全检查），预推送钩子负责阻止未过关的提交；主 Agent 不接受实现 Agent 的口头汇报，会重新跑验证、看 diff，在桌面与手机宽度、亮色与暗色主题下走一遍浏览器；另一个没有实现上下文的 Agent 复看变更。[1]

这些检查找出了同页两个表单重复的 id，以及 32 像素的复制按钮挨着 40 像素输入框等问题。但**它们仍没有发现外部模型调用失败后业务被标为成功**。所以作者把自己必须操作的密钥、支付配置与真实手工检查集中到单独清单，不在编码中途被反复打断；最后要求 Agent 交付一份端到端检查脚本，由他在部署前执行一次。[1]

## 下一次交付，可以少问一句“测试过了吗”

原案例值得直接借用的不是目录命名，也不是多安排几个审查 Agent，而是**把“完成”的判断绑定到真实业务结果**。例如让 Agent 实现“生成一次报告并通知用户”，任务中可以明确要求：

> 开发时运行项目的快速测试和 `bin/ci`。交付前，用测试账号执行一次完整的报告生成流程；保留请求状态、实际返回、生成产物及通知的证据。再模拟上游模型超时、无效凭证或空响应：任务必须停留在失败/待重试状态，不得发送“完成”通知，不得消耗一次性权益，不得用空数据生成建议。若无法访问真实服务，写明 NOT_RUN 与缺少的条件，不准将 stub 成功写成端到端成功。

这是**根据案例提炼的示范指令，不是作者的原始提示词**。它和“跑全量测试”并不冲突：前者检验真实依赖与业务状态，后者保护大量可重复的内部逻辑。Martin Fowler 对测试金字塔的解释也指出：stub 能让测试快速、稳定，但测试替身与真正的第三方接口行为可能不同，因此还需要对真实集成点的检查。[3]

可以把验收结果拆成三张证据，而非三份长报告：**代码证据**（CI 及 diff）、**交互证据**（浏览器真实路径）、**失败证据**（外部依赖断开时的业务状态）。对失败场景，不必在生产系统上制造事故：在隔离的测试环境使用专用账号、限额和可控故障注入即可。对于需要人工授权的密钥、价格和部署操作，保留明确的人类确认点。[1][3]

## 为什么这能减少无效往返，但还不能说提高了多少效率

LLM 生成测试时，通常会偏向它刚写出来、最容易构造的成功路径；stub 又使每一次外部调用都稳定返回“合理”内容。主 Agent 即使重跑同一组测试，也只是在重复验证相同假设。作者的真实手工检查提供了一个开发会话无法凭空推出的事实：**外部服务此时不可用，而完成状态与权益扣减仍然发生。**

记录下来的三个错误分别对应：依赖可用性、失败后的业务状态、用户上下文污染。修复它们要求 Agent 不只改提示词，还要补明确的失败断言。具体哪些规则要写入测试、哪些异常要人工确认，必须由产品需求决定。

这项实践的收益有边界。作者称这三天没有亲手写代码，并让 Agent 把需要他处理的事项批量收口；但没有发布人工投入分钟数、代理会话费用、返工成本与对照工期。111 次提交或 3,207 条绿灯也不是人的生产率指标。特别是那个真实故障，说明流程尚未达到可对外宣布完成的状态。这里能验证的是**故障发现的路径与协作职责**，不是固定的提效比例。[1]

独立核查方面，Anthropic 官方文档支持“启动目录影响项目指令加载”，测试工程资料支持“模拟服务不等于真实集成”。但没有找到针对 Ash 这次 2.0 开发的独立社区复盘或原始 CI、PR 审计，个案数字仍属作者自报，不能把机制交叉验证写成结果复现。[2][3]

## 明天可直接试的三个动作

1. **交任务时补一个业务失败例子。** 不只写“生成报告”，还写“依赖返回空值或错误时，用户看见什么、什么绝不能发生”。
2. **让 Agent 在正确的产品目录启动，并自己跑完快速闭环。** 要求提交 CI 输出、变更摘要和真实界面路径；别把它的“已通过”当作日志。
3. **把人工介入合并为最后一次验收。** Agent 先整理真实环境必需的凭据和步骤；人用隔离账号跑一次成功路径、一次故障路径。没跑到就标 NOT_RUN，不能标 DONE。

作者最后的反思是：他会更早在真实依赖和失败路径上测试，而不是把这些检查留到代码已经写完。这一条比“让 Agent 多写一点测试”具体得多。

# 代码审查 Agent 不必越复杂越好：半年 1306 条评论，为什么最后只留一个简单 Skill

**一句话结论：别用“Agent 找到了多少问题”评价代码审查。看评论有没有推动这次 PR 发生有价值的修改，还要看它为人增加了多少阅读与判断负担。** 这适用于经常用 Agent 审查 PR、已经积累多套审查提示词或 Skills 的开发者，尤其是正在考虑再加一批并行审查子 Agent 的人。

Anago 在两个代码仓——移动应用与后端——给 PR 审查写了三个 Skill，连续使用半年后重新统计。结果颇有讽刺意味：最简单的 `review-pr` 有 **68.9%** 的评论引发后续代码修改；并行 11–14 个审查视角的 `deep-review` 只有 **59.2%**。作者最后停用了复杂版和只挑细节的版本，留下定时运行的基础审查。[原文，2026-11-15](https://zenn.dev/mizo_ko/articles/article-105-zenn)

这不是“简单 Skill 一定更强”的实验结论。它更像一次面对真实工作账本的止损：**多查出来的内容，究竟值不值得人读、判断和处理？**

## 旧做法：为更全面的审查不断叠加视角

作者曾经沿着很自然的方向扩展审查能力：

- `review-pr`：沿着 PR 的代码行找问题，基础款。
- `deep-review`：把审查拆成不同视角，交给子 Agent 并行处理；视角从 11 个增加到 14 个。
- `nitpick-pr`：专查格式、写法等琐碎问题。

复杂版确实给出了更多意见：每个 PR 平均 **7.8 条**，基础版 **4.4 条**，约为后者的 1.8 倍。站在模型输出端看，这像是审查覆盖面增加；站在 PR 作者端看，意味着每次多读约三条意见，逐条判断是否正确、是否属于当前改动、是否值得调整，再修改代码和重跑验证。

这里的浪费不是“Agent 出错”一种情况。有些意见**技术上正确，却不属于这次 PR 的目标**；还有些修改本来可以做，但收益小到不值得引入新的改动风险。Agent 很容易把“我还能提出一个问题”误当作“人应该现在修复它”。

## 他没有凭印象选 Skill，而是把评论追到后续提交

作者先统一历史统计口径，再重新核对 2026 年 4 月至 11 月 13 日的审查记录。最初有 **1,691 条评论**，剔除未合并 PR 的 271 条、PR 作者没有回复的 112 条、机器人 PR 的 2 条，余下 **1,306 条**。自己给自己提的审查意见也算在内。

关键定义是：只有评论之后**确实出现相应代码变更**，才记为“被修改”。作者结合 PR 回复和后续 commit 判断，而不是用 Agent 自己宣称的“问题已修复”计数。

| 审查 Skill | 评论数 | 平均每 PR 评论 | 后续发生修改 | 修改比例 | 误报比例 |
|---|---:|---:|---:|---:|---:|
| `review-pr` | 354 | 4.4 | 244 | **68.9%** | 9.6% |
| `nitpick-pr` | 114 | 2.8 | 76 | 66.7% | 9.6% |
| `deep-review` | 368 | 7.8 | 218 | **59.2%** | 9.8% |
| 全部评论（含无法归属来源） | 1,306 | 9.7 | 789 | 60.4% | 11.2% |

*数据来自作者的回溯统计，不是本次独立复算。三组可识别 Skill 评论共 836 条，其余约 36% 无法识别由哪个 Skill 产生，不应拿全体行与单个 Skill 做严格对照。*

最有用的不是两组修改率相差 9.7 个百分点，而是**误报率几乎相同**：三种 Skill 都在约 10%。复杂审查并没有通过更低的误报率证明额外开销合理。

作者进一步给未修改的评论分类。`deep-review` 中“判断没错，但优先级低或超出本 PR 范围”的比例是 **17.4%**；基础版只有 **6.2%**；细节版为 **16.7%**。复杂版多出来的审查意见，恰恰更容易落入“知道了，但现在不做”的区域。

## 两个反例，比漂亮的采纳率更值得记住

**第一，审查 Agent 可能在看错误的时间点。** 八月，基础 Skill 有 15 条误报，其中 8 条集中在两个 PR：移动端 PR 的 5 条中，3 条引用了旧 commit、问题早已修复，另 2 条把预期行为当成缺陷；后端 PR 的另 3 条援引错误先例，被撤回。九月以后基础版误报率回到 0%–5.6%，但作者明确说没有记录导致变化的调整，不能据此编造“某种提示词修好了误报”。

这给读者一个直接的检查点：**收到审查建议，先确认它对应的是当前 diff、当前行为和当前任务。** 这不要求人逐行指导 Agent，却能阻止基于过时上下文的返工。

**第二，采纳率高，也可能只是在制造琐事。** `nitpick-pr` 的修改比例是 66.7%，乍看仅次于基础版；但它主要促成格式和细节修改，发现不了关键缺陷。作者仍然把它停掉。评论被修改只说明“产生了动作”，并不证明“动作有价值”。相反，一个涉及真实数据损坏的意见即使暂时没改，也未必是低质量意见。

因此，作者决定下一步不再只盯评论数量，而要补上**严重程度**。这是他后续准备完善的判断，不是本文数据已验证的指标。

## 为什么减法可能让整项工作更快

对这次案例，更合理的解释不是“子 Agent 变笨了”，而是**生成意见的边际成本和处理意见的边际成本不同**。

模型可以并行枚举很多检查视角，但每条建议最终都要落到一个具体 PR：它涉及哪个调用方？是否触及本次变更边界？修复风险是否大于收益？这些问题仍消耗人的注意力和 CI 反馈周期。并行生成能缩短部分模型等待，却未必降低“从收到意见到放心合并”的总耗时。

而且审查 Skill 并不天然拥有完整、最新的项目状态。长上下文里混着旧提交、相似实现和不完整业务意图时，模型可能引用似是而非的证据；更多并行视角还会生成重复或彼此冲突的意见。八月那八条误报提供了实际例子，但不能证明并行本身就是根因。

作者留下的不是更复杂的审查流水线，而是**一个按固定时间运行的基础 Skill，以及可以按月重复计算的逐条判定数据和脚本**。这把人的工作从“维护越来越多审查规则”，转到“判断哪些反馈值得继续获得”。注意：脚本和原始逐条记录并未公开，不能据此声称这套统计已经被独立复现。

## 明天就能做的最小调整

如果你已经把 Codex、Claude Code 或其他 Agent 接到 PR 审查里，可以先不增加新 Skill，拿最近一批已完成的 PR 做一次小规模对照：

1. **统一记录单位。** 每条 Agent 评论保留来源 Skill、对应 commit / diff、问题类别、PR 回复和后续相关代码变更。没有证据就记“无法判断”，不要自动记作已修复。
2. **把两项数字放在一起。** 看“每 PR 评论条数”和“真正促成相关变更的比例”；另外抽查“正确但低优先级 / 超范围”的评论。避免只比误报率或评论总量。
3. **拒绝一键照单全修。** 在改代码之前，让 Agent 说明这条意见与当前 PR 目标的关系；关联不清就交给人取舍，不把审查模型的建议自动升级成需求。
4. **再决定删什么。** 若某套复杂 Skill 主要增加低价值评论，先停用观察，而不是继续追加审查视角。关键缺陷和回归漏检仍需另行检查，不能用“修改率低”直接判死刑。

这四步是根据作者方法整理的试用建议，**不是作者公开证实的最优流程**。

## 独立反馈与证据边界

独立整理站 [Working Surface](https://workingsurface.ai/links/2026-11-16-01/) 回溯了原文的统计口径，也指出 36% 无法归属 Skill，以及“已修改”判断的噪声。另一则 [Reddit 开发者讨论](https://www.reddit.com/r/ClaudeCode/comments/1xzdi6c/claude_code_is_design_to_make_you_dump/) 描述了深度审查提出边缘问题、Agent 随后自动修复反而使代码更复杂的体验。这些材料提供**相似问题的独立观察**，不是对 Anago 这 1,306 条评论的独立复测。

必须保留三个限制：只选“合并且回复”的 PR，天然排除了可能更难处理的评论；约 36% 的评论无法归属 Skill，三种 Skill 也没有在同一批 PR 上随机对照；作者抽查 8 条“已修改”判定，发现 **2 条其实是无关代码变更**。因此 68.9% 和 59.2% 只能当作该批数据的描述性结果，不能换算成通用提效比例。

原文没有披露模型及 Skill 的准确版本，也没有总工时、token 费用、人工审查耗时、线上缺陷率或漏报严重问题的数据。**这项实践证明的是作者如何根据真实后续行动淘汰 Skill，尚未证明一个 Skill 在所有项目中都会比多 Agent 审查更好。**

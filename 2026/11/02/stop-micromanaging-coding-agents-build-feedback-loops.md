# 从逐步盯进度到只处理例外：一位开发者如何同时驱动多个编码 Agent

**一句话结论：别再靠自己频繁检查 Agent 的每个中间步骤来获得信心。先把目标、项目惯例、真实运行反馈和验收边界交代清楚，让它自主完成“实现—测试—观察—修复”；人只处理方向分歧、关键路径和不可逆决定。** 适合能运行项目、能获取故障信号、有安全回滚条件的开发者。没有这些前提，先补最短的一条反馈链，不要直接打开生产自动部署。

这不是一句“模型变强了，所以放手”的口号。Victor Martin Garcia 在 2026 年 10 月 27 日写下八个月前后对比：从详细 Plan Mode、分段任务和逐次合并审核，转向先谈目标和约束，再让 Claude Code、Codex 自行实现、运行、调试和部署。他说自己的瓶颈不再是代码产出，而是**同时跟进多个项目时，人还能否保持足够的判断力**。[1]

## 他到底停止做了什么？

对照作者 2 月的旧文和 10 月更新，可以看见变化不是换了一套提示词：

| 过去：人负责过程 | 现在：人负责边界 |
| --- | --- |
| 先生成详细计划，人逐项看过才开始 | 先讨论目标、关键取舍和约束；不再逐项批准实现计划 |
| 人把需求拆成小任务、逐段检查 | Agent 自行选择步骤，直至验证与交付 |
| 人逐次审核合并 | 普通变更依靠既有检查；关键路径仍由人测试和批准 |
| 生产报警由人排查，再指挥 Agent 改 | Agent 读取错误、日志、代码、部署历史，提出修复并验证 |
| 人盯终端等待多个会话 | 多会话持续运行，只关注阻塞、完成和需要决策的状态 |

2 月的文章还把“小块任务、逐次复核”列为重要经验。[2] 10 月作者没有声称这些技术彻底过时；他强调自己的技术栈、检查和运维反馈已经足够成熟，可以让 Agent 独立完成更长的一段工作。这一点比“不要用 Plan Mode”更值得借鉴。

## 第一项改变：目标谈清楚以后，不再替 Agent 拆每一步

作者现在通常先问“我想做这个，你怎么看，会怎么做？”，一起讨论架构取舍和隐藏问题。达成一致后，他交给 Agent 的是**整个交付周期**，而不是“先改文件 A，等我看完再改文件 B”。

这种做法并不等于只给一句“修好它”。真正有用的是把下面几类信息放在任务入口：用户要观察到的结果、不能破坏的行为、技术约束，以及什么决定必须再问人。至于从哪里读代码、选哪种测试、如何排查，则允许 Agent 自主安排。

下面是依据原文整理的**可改写任务表达，不是作者逐字使用的 Prompt**：

> 针对这次错误，先用现有日志和可运行环境确认原因，然后完成修复、相关回归检查和可复验的端到端验证。实现步骤由你决定。请给出故障证据、修改依据、实际运行结果和仍未验证的部分。不得为通过测试而删除或降低既有检查；涉及生产发布、数据变更或难以撤销的操作，先提交方案和证据，等待批准。

这段文字刻意不列读取文件顺序，也不指定修复算法。它只固定目标和验收边界。作者的实际做法对自己可控的常规变更给了更大的发布自主权；上面的模板对一般团队则保留了发布批准，不应混称为原作者的原话。

## 第二项改变：给 Agent 可观测的真实世界，而不是不断喂说明

作者所依赖的工作环境有四部分：统一技术栈与架构惯例、可以本地运行的应用和自动化检查、Sentry/Grafana/日志/部署工具，以及持续维护这些能力的文档和 Skill。[1]

这里最实际的价值是**人不再担当日志搬运工**。一个 Agent 如果只能看到源码，就只能猜测服务在生产环境是否经过了这段代码；如果它能读取 Sentry 事件、相关日志和部署历史，就可以按证据排查。单元测试、端到端测试、属性测试与 Makefile 提供本地复现入口，蓝绿部署与回滚则给发布后的验证提供缓冲。

作者举了一个生产例子：定时任务每隔几分钟检查 Sentry；发现新错误后，Agent 读错误、日志、代码和发布历史，修复、测试、部署，再由作者事后查看发生了什么。[1] 这是一条**作者报告已在运行的工作流**，但原文没有开放该事件的全部日志、补丁和部署记录，也没有公布自动修复成功率。

要迁移到自己的项目，我建议分四级开放，而不是第一天复制“无人值守上线”：

1. **调查级**：只读日志、检索代码、复现，交付定位证据。
2. **修复级**：允许改开发分支、运行测试、提交 PR。
3. **预发布级**：允许部署隔离环境，观察真实请求与错误指标。
4. **有限发布级**：只对已证明可回滚、影响范围明确的低风险变更开放自动发布。

四级是本文的迁移建议，不是作者报告的部署分级。让 Agent 多读事实和让 Agent 获得不可逆写权限，是两件不同的事。

## 第三项改变：把人工审批留在真正需要判断的地方

Victor 给出的决策边界很干脆：普通变更走自动检查；**关键路径自己测试并批准**；削弱或删除检查必须询问他；难以撤销的决定找另一个模型提出反对意见；生产报错则让 Agent 先查。[1]

有个细节不能忽略：作者说“不得削弱检查”写在 Agent 指令中，但没有公开证明所有检查都由不可绕过的独立系统强制执行。语言规则对合作中的 Agent 有作用，**却不是权限隔离或防篡改机制**。对于严肃仓库，最好把受保护测试、合并规则和发布权限放在 Agent 无法单独改写的执行端。

另一个看似矛盾的地方也值得保留：他不再逐次审阅所有代码，却仍会用**不同模型**审视重要架构假设，追问“是不是走错了方向”。这不是让第二个 Agent 做一遍相同代码审查，而是让它找第一种解释的反例。独立模型并不保证独立错误，但能提供另一种调查路径。

## 第四项改变：多个会话同时工作，人的注意力开始比算力更贵

作者报告：最近 30 天，仅其笔记本上的 Agent 就涉及约 **20 个项目、600 次提交、170 次部署**，通常一天处理 4 个项目，忙时同时运行最多 9 个会话；远程服务器上的会话未计入。[1] 这些是他的工作量统计，**不是验收通过数，更不能直接换算为节省的人时**。我们没有看到对应的原始任务清单、回滚次数或缺陷统计。

他通过 herdr 管理 Claude Code 和 Codex 会话：按项目组织、按最近活动排序，并将工作中、已完成、需要输入等状态放在一起。用 Tailscale 和 SSH 从手机连接，配合语音输入和一个小手柄切换会话。[1] 真正改善体验的不是手柄，而是**不用反复打开每个终端确认有没有卡住**。

这部分有可独立核查的开源实现：herdr 仓库公开了终端工作区、状态显示、后台会话、分离与重连的代码和说明。[3] 当前文档给出的基础用法是：

    herdr
    # 在界面内以 Ctrl+B 再按 Q 分离
    # 之后重新执行 herdr 连接后台会话

也可以通过 SSH 进入运行机器再打开 herdr。**注意：分离终端不等于快照了任务。**原进程能否继续运行取决于后台服务和机器状态；机器重启后的布局恢复、Agent 原生会话续接，与原进程继续执行并不是同一保证。[3] herdr 具体版本在作者文章中未披露，不能把目前仓库的全部能力倒推为他 10 月 27 日的配置。

这里的工作原则与独立工程文章《Humans and Agents in Software Engineering Loops》相呼应：人从逐行监督转向设计工作反馈和验收系统。[4] **这只能算方法上的独立呼应，不是对 Victor 的 600 次提交或生产效率的外部复验。**

## 怎么判断自己是否真的更高效了？

如果一次委派让 Agent 连续工作 40 分钟，却让人每两分钟答一次问题，自动化可能只是把键盘劳动换成了注意力消耗。相反，某次任务虽然调用成本较高，但人只需讨论一次目标、最终检查一次证据，整项工作可能更划算。

建议从连续十个真实任务记起：记录从委派到可接受交付的耗时、人的介入次数和分钟数、因不满足验收而返工的次数、回滚或补救次数；把最终被接受的结果作为分母。**这些是应当测量的指标，不是原文已经报告的改善数字。**并行会话数与提交量只说明工作在运行，不能说明它做对了。

## 明天可以直接尝试的五件事

- 选一个能本地复现、风险低的任务，不要从生产权限入手。
- 只讨论目标、约束、关键架构决定和验收结果；让 Agent 自行安排实现与测试顺序。
- 让 Agent 能亲自运行项目、看日志、重现错误，而不是让人贴终端输出。
- 约定什么时候必须停下来问人：关键业务路径、削弱既有检查、难以撤销的动作。
- 多会话只看“卡住／需要决策／完成”的摘要；一周后检查实际人工时间和返工，而非炫耀跑了多少 Agent。

**适用边界：**这是一位能统一技术栈、控制基础设施的小团队开发者的个人实践。大型遗留系统、强监管环境、缺少回滚和可观测性的项目，不能直接复用其生产自主发布强度。原文提供了可信的一手流程和具体工作量，但缺少可复验的效率对照；本次也未运行作者的项目或验证其部署成绩。因此结论应限定为：**这是一种值得试验的协作方式，而不是已被证明可普遍复制的生产率倍率。**
